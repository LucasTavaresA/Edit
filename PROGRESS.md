# PROGRESS

Progress tracker for **Edit** — a bare text editor for Android that opens and closes encrypted files in a format any tool can read and sync.

## Where the project stands

A working bare editor: open a file, edit it, save it.

- `com.lucasta.edit`, AGP 9.3.1, Gradle 9.7.0, Kotlin 2.4.10 (compiled by AGP's built-in Kotlin support)
- minSdk 26, compileSdk 37, targetSdk 37
- Compose UI and foundation 1.11.4, material3 1.4.0. Five dependencies are declared — the Compose BOM, `ui`, `foundation`, `material3`, `activity-compose` and `kotlinx-coroutines-android` — matching what the source imports. core-ktx and lifecycle arrive transitively at 1.18.0 and 2.9.4.
- Source is two files: `MainActivity.kt` (edge-to-edge setup, theming and the editor UI) and `TextFile.kt` (encoding detection, strict read, write, display name). The theme is four lines inline in `onCreate`, not its own file or package.
- **The app follows the system light/dark setting.** Three pieces have to agree or the result is unreadable, so all three changed together: `MaterialTheme` over a full-size `Surface` for the Compose side; `res/values/themes.xml` and `res/values-night/themes.xml` defining `Theme.Edit` over `Theme.Material.Light.NoActionBar` and `Theme.Material.NoActionBar` so the window background is already the right colour before Compose draws; and `SystemBarStyle.auto` for the bar icons.
- **It follows the wallpaper palette too, where the platform has one.** `systemColorScheme()` in `MainActivity.kt` is a single `Build.VERSION.SDK_INT >= S` check: from API 31 it returns `dynamicDarkColorScheme(context)` or `dynamicLightColorScheme(context)`, and below that it falls through to the stock `darkColorScheme()` / `lightColorScheme()` baselines. Nothing is configured, stored or exposed as a setting — older devices simply get the Material default. Confirmed on API 34, which takes the dynamic branch: the accents follow the wallpaper rather than the baseline purple.
- **`BasicTextField` needs its colours passed explicitly.** It comes from foundation, which knows nothing about material3, so its default text colour and `cursorBrush` are black regardless of theme — black text on a dark surface. Both are wired to `LocalContentColor.current`, which the `Surface` sets from the scheme. Any future foundation-level widget needs the same treatment; material3 composables get it for free.
- **Edge-to-edge is on for every device**, via `enableEdgeToEdge()` with `SystemBarStyle.auto(TRANSPARENT, TRANSPARENT)` for both bars, and `Modifier.safeDrawingPadding()` keeping content out from under them. `auto` reads the system dark theme to decide icon colour, which is now correct because the app follows it too — it was pinned to `light` back when the app was light-only. Dark icons on both bars need API 26, which is minSdk, so the scrim colours are never reached.
- **Debug carries `applicationIdSuffix = ".debug"`**, so `com.lucasta.edit.debug` installs alongside the release `com.lucasta.edit` instead of colliding with it. Before this, `adb install -r` of a debug APK failed with `INSTALL_FAILED_UPDATE_INCOMPATIBLE` because the two are signed with different keys, and the only way through was to build release. The launcher label is `@string/app_name`, set per build type via `resValue` to "Edit debug" and "Edit" — AGP 9 requires `buildFeatures { resValues = true }` for that, or configuration fails with "Build Type debug contains custom resource values, but the feature is disabled". Note the component to launch is `com.lucasta.edit.debug/com.lucasta.edit.MainActivity`: the suffix moves the application id, not the class.
- Debug APK builds green with no compiler warnings (`app/build/outputs/apk/debug/app-debug.apk`, 11.5 MB unminified), about 2m40s from clean and well under a minute incremental
- Release builds too, minified by R8 and signed, at 1.5 MB. No proguard rules of our own were needed — AndroidX and Compose ship their own consumer rules. Verified by dumping the APK, by `apksigner verify` (v2 scheme), and by installing it over adb and confirming it launches with nothing in logcat. **But see the OOM note below — do not build release casually.** The installed release is therefore behind the debug one, and will stay that way until there is a reason to ship.
- No tests and no test dependencies. No crypto code yet.

## Design decisions

- **Encryption format must be tool-agnostic.** A single self-contained file (age, or AES-GCM + Argon2id envelope) that any desktop tool can decrypt. Explicitly NOT Jetpack Security / `EncryptedFile` — it binds keys to the device keystore, making files unreadable off-device.
- **File access via SAF**, so no storage permissions and any sync tool (Syncthing, rclone, etc.) owns the files.

## Environment

Everything below is plain `pkg install` or a stock SDK — no hand-assembled pieces, no version fictions, nothing that needs to be worked around.

- **Build with `gradle assembleDebug` from the project root.** No flags, no property overrides on the command line. A clean build is about 2m40s, which is long enough to want a background run; incremental is well under a minute.
- **`gradle assembleRelease` gets the low-memory killer to take out everything on the device**, including the terminal, even with Termux set to unrestricted power mode. R8 plus the AGP daemon on top of an already loaded device is simply too much. So release is not a build we run to check our work — that is what the debug app is for. Only build release when there is an actual reason to ship one, expect to lose the session when you do, and do not casually run it for verification.
- **`adb shell cmd uimode night yes|no` flips the system dark theme**, which is how the light and dark paths were both checked without touching the phone by hand. It is a global setting, so put it back when done.
- Gradle 9.7.0 comes from `pkg install gradle` — the same version `gradle-wrapper.properties` pins. `gradlew` is still in the repo and correct for anyone else, but the wrapper distribution was never downloaded here, so `./gradlew` would pull 130 MB from `services.gradle.org` to arrive at the same Gradle. The termux mirror runs about 10x faster than Google's, which is why the packaged one won.
- JDK is `openjdk-21` (21.0.12). AGP compiles to JVM 17 bytecode regardless, per `compileOptions` and the `kotlin` block.
- **aapt2 is `pkg install aapt2`**, a native aarch64 build reporting `2.20-android-16.0.0_r4` — genuinely build-tools 36 era, which is what AGP 9 expects. `optimizeReleaseResources` runs and produces a correct APK, so the old `android.enableResourceOptimizations=false` workaround is gone.
- The one setting that has to stay is `android.aapt2FromMavenOverride`, pointing at `/data/data/com.termux/files/usr/bin/aapt2`. AGP's own aapt2 comes from Maven as a glibc x86_64 binary that cannot run under bionic, so without the override every build dies in `processDebugResources`. It lives in `~/.gradle/gradle.properties`, not in the repo, because it is an absolute path for this machine only.
- **SDK is at `~/android-sdk`, installed by a real `sdkmanager`** (cmdline-tools 22.0). `local.properties` points at it, so no `ANDROID_HOME` is needed. The cmdline-tools scripts ship a `#!/usr/bin/env` shebang that termux cannot resolve; `termux-fix-shebang` on `cmdline-tools/latest/bin/*` fixes it once.
- `platforms;android-37.0` is installed properly, with `package.xml`. `compileSdk = 37` resolves to `android-37.0` specifically — `android-37.1`, the Android 17 minor release, does not satisfy it.
- **AGP auto-installs `build-tools;36.0.0` and `platform-tools`, and both are x86_64.** Nothing executes them: aapt2 comes from the override and D8, R8 and apksigner are JVM tools. The debug build in fact succeeded before build-tools existed at all. Worth remembering only if some future AGP task shells out to a native build-tools binary, which would fail with an exec format error.
- **Nothing installs an APK from the termux shell except adb.** Four routes were tried and each is walled off differently. `pm install` fails because SELinux denies `system_server` access to `app_data_file`, so it cannot read the build dir; it suggests `/data/local/tmp`, which an app uid cannot write to. `content query`, which would get a MediaStore URI the way a file manager does, needs the privileged `ACCESS_CONTENT_PROVIDERS_EXTERNALLY`. `am start` is refused because it identifies as `com.android.shell` while running as our uid, so `assertPackageMatchesCallingUid` throws. `termux-open` does raise the install prompt — Termux has "install unknown apps" granted — but the installer rejects its FileProvider URI, with or without an explicit `--content-type`, and whether the APK sits in the build dir or in `~/storage/downloads`. The installer only accepts a `content://` URI, Termux's provider is the one it refuses, and every tool that could mint an acceptable URI needs a privileged permission.
- **"Invalid package" from the installer does not mean the APK is bad.** The same file that fails through `termux-open` installs fine when copied to `~/storage/downloads` and tapped in a file manager. It is a delivery failure wearing the costume of a corrupt build: `resources.arsc` compression, native library alignment and signatures were all correct.
- **adb is paired and this is now the way we install.** `pkg install android-tools`, a native aarch64 build. `adb install -r app/build/outputs/apk/release/app-release.apk` streams the APK over a socket rather than handing over a path or a URI, so none of the walls above apply and it works straight from the build dir with no copying and no tapping. `adb shell am start -n com.lucasta.edit/.MainActivity` launches it, and `adb logcat` finally gives us crash output.
- **Reconnecting after a reboot or a Wireless debugging toggle.** Pairing itself survives, but the connect port changes every time, so it needs `adb connect <ip>:<connect-port>` with the port read off the main Wireless debugging screen. That screen is not a popup, so it can be read after switching apps. This adb has no mDNS support, so `adb mdns services` errors out and the port cannot be discovered automatically. The adb server also dies on its own between commands here — when a command reports `daemon not running; starting now` and then `no devices/emulators found`, the fix is just `adb connect` again on the same port, which is still valid. Cheap enough to prefix onto any adb command after a gap.
- **Pairing again, if it is ever needed, requires split screen.** Android invalidates the pairing session the instant the pairing dialog is dismissed, and switching apps dismisses it — so the code can never be relayed by switching to the terminal. What that failure looks like is `error: protocol fault (couldn't read status message)`, which reads like a broken adb and is not one; the termux issue for it is closed as not-bug. Put Settings and the terminal side by side in split screen, then run `adb pair <ip>:<pair-port> <code>` while the dialog is still on screen. The pairing port and the connect port are different.
- Falling back without adb means `cp` to `~/storage/downloads` and tapping the file by hand in a file manager.

## Known limits of the current editor

1. **Only files that survive a byte-exact round trip will open at all.** A file with a few corrupt bytes is refused outright, even though it might be worth reading. There is a TODO in `TextFile.kt` for offering to open it anyway as a deliberate choice, with a clear warning that saving will rewrite the bytes that could not be represented and that a backup must exist first.
2. Legacy single-byte encodings are rejected. Latin-1 and Windows-1252 accept any byte sequence, so they cannot be detected, only guessed at. A file of Latin-1 accented text will simply refuse to open.
3. No unsaved-changes tracking, so opening a second file silently throws away edits to the first.
4. The whole file is read into one String, so large files will hurt.
5. No persistable URI permission is taken, so a file cannot be reopened after the process dies. Harmless until there is a recent-files list to reopen from.

## Not started

- `ACTION_VIEW` / `ACTION_EDIT` intent filters for text MIME types
- Editor UI (large-file handling, undo, find)
- Encryption: passphrase entry, KDF, envelope format, decrypt-on-open / encrypt-on-close
- Device-to-device backup posture. `allowBackup="false"` stops cloud backup on every supported version, but from Android 12 it does not stop device-to-device transfer — that needs `android:dataExtractionRules` with a `<device-transfer>` exclude, which costs an XML file. The app persists nothing at all today, so there is nothing to leak; do this when it first stores something, such as recent files, SAF permission grants or settings.
