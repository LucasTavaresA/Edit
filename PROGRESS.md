# PROGRESS

Progress tracker for **Edit** — a bare text editor for Android that opens and closes encrypted files in a format any tool can read and sync.

## Where the project stands

A working bare editor: open a file, edit it, save it, undo it. The document is the file where it lies plus a list of the changes made to it, so how large a file can be opened stopped being a question about memory — and the window that takes the typing follows the cursor wherever it goes, so how much can be edited in one place stopped being a question at all.

- **Everything is on its latest stable release, checked against the actual repos rather than assumed.** AGP 9.3.1 (9.4.0 exists only as alphas), Gradle 9.7.0, Kotlin 2.4.10 (2.4.20 is Beta/RC), activity-compose 1.13.0, coroutines 1.11.0, Compose BOM 2026.08.00. Do not read the tail of a `maven-metadata.xml` and call it the latest — the `<release>` and `<latest>` tags there point at prereleases too; AGP's both said `9.4.0-alpha08`. Filter for stable explicitly.
- Source is ten files. Four are pure Kotlin with no Android in them, which is deliberate — they are where a mistake corrupts a file quietly rather than crashing, so they are kept free of anything Android: `Encoding.kt` (what a file is written in, and the arithmetic that follows), `Pieces.kt` (the sequence of pieces, the splice, the changes made to it and the compaction of what was typed), `Chunks.kt` (the chunk index over bytes) and `Slice.kt` (decoding a run for the screen, and the map back). The other six are the Android side: `Content.kt` (the open descriptor and the document built on it), `Document.kt` (vocabulary, caps, open and save dispatch, the collision check), `TextFile.kt` (the plain path), `EncryptedFile.kt` (stubs), `Editor.kt` (`DocumentState` and the composables) and `MainActivity.kt` (theming, toolbar, wiring). The theme is a handful of lines inline in `onCreate`, not its own file or package.
- **Release builds again.** Minified by R8, resources shrunk, verifying under the v2 scheme, at 1.2 MB. No proguard rules of our own were needed; AndroidX and Compose ship their own consumer rules.
- **`isShrinkResources = true` is now exercised and both worries about it were unfounded.** The launcher icon is in the APK, under a shortened path that `optimizeReleaseResources` gives it — `res/d2.webp` and the like, which is why looking for `mipmap` in a file listing finds nothing and means nothing. `values-night/themes.xml` survived too: the resource table has `style/Theme.Edit` with both a default and a `(night)` configuration, the night one carrying the black window background.
- No tests and no test dependencies. No crypto code yet.

## Design decisions

- **The document is the file plus its changes, and it behaves as a whole copy of the file taken the instant it was opened.** What a save writes is that copy with our edits in it and not one byte from anywhere else — never something another tool put there in the meantime, whether it appended, rewrote or replaced. The change list is only how a copy that large is afforded.
- **Coordinates are bytes.** A piece is a byte range whichever side it points at, so a range nobody edited is copied to the output exactly as it came in and only the parts that were touched are ever decoded or encoded. That makes a save incapable of corrupting what was not edited, and it makes a file that no decoder round-trips openable and editable. The cost is that everything looking for a line break has to look in code units and not in bytes, since in UTF-16 a byte 0x0A is only sometimes a line break, and that every tap and every cursor has to cross between characters and bytes.
- **Crossing between characters and bytes is arithmetic, not a table.** A strict decode is a bijection, so what a run of characters weighs in bytes can be counted without encoding it, and the map a slice carries has an entry only where the decoding was *not* a bijection — one per byte the encoding could not name. Ordinary text carries no entries at all. What makes that safe is that the arithmetic has to agree with the encoder on *every* input and not only on well-formed input, unpaired surrogates included.
- **A file that does not decode is opened anyway, and that is now the default rather than a deliberate choice.** The old refusal existed because the whole file was decoded on the way in and re-encoded on the way out, which made every byte the decoder could not name a byte that saving would destroy. Under byte addressing that is no longer true, so a file with a few bad bytes in it, or one in a single-byte encoding nobody can detect, opens and reads and is safe to edit somewhere else. What refuses a file instead is one zero code unit in its first 64 KB: text does not contain one and everything that is not text is full of them, and it is a rule about the file rather than about the decoder.
- **A file we cannot seek in is not opened, and this is settled.** Every provider backed by a real file on the phone gives a seekable descriptor, which is every file this app exists for; the ones that stream their content instead are refused with a message.
- **The open descriptor is the snapshot, so nothing is copied and opening stays fast.** A descriptor pins the file it was opened on, not the name: a tool that replaces the file — writing a temporary and renaming over it, which is what Syncthing and rclone do — leaves what we are reading alive and intact until we close it, whatever the name now points at. That is a real snapshot for the price of holding one descriptor. The bytes stay on disk rather than in memory, so it costs the space of the replaced file until the document is closed.
- **A tool that writes in place is the case a descriptor cannot cover, and it is `fstat` that catches it, not a hash.** Size and modification time read back off our own descriptor say so for nothing — where a hash costs a full read of the file to learn the same thing, and could still only ever say that bytes are gone, never bring them back. So it is refused with a message and the document is not silently half old and half new. The granularity is a second, so a tool that rewrites in place within the same second as the open, without changing the size, would not be caught.
- **A save onto a file that changed since it was opened asks first: overwrite, save as, or cancel.** This is the ordinary collision — sync brought a newer version while the document was open — and the document itself is fine, since the descriptor kept it; the only question is whose version the file ends up holding, and that is the user's to answer, not ours. Device and inode taken at open are what the question is asked from, which is the exact test for "replaced" rather than a guess from size and time.
- **Saving is the one place a copy is unavoidable, and afterwards the document starts again from what was written.** Writing through SAF truncates the file our own pieces still point into, so the output goes to a temporary in the app's storage and is copied over the file afterwards. That is two passes for a save and the file's size in space while it runs, and it buys back that the file is only touched once there is a whole document to put in it. The document then re-opens the file it just wrote and collapses back to one piece; if that re-open finds a file of the wrong size — something got in between — it keeps the temporary as its snapshot instead, unlinked, and leaves the file unstamped so the next save asks rather than assumes.
- **The encrypted path keeps its own model** — decrypted whole, in memory, never a byte of plaintext on disk. It is the same `Content` with every piece pointing at the typed buffer and none at a file. No pieces into a file, and nothing written anywhere, temporaries included, that is not ciphertext.
- **Encryption format must be tool-agnostic.** A single self-contained file (age, or AES-GCM + Argon2id envelope) that any desktop tool can decrypt. Explicitly NOT Jetpack Security / `EncryptedFile` — it binds keys to the device keystore, making files unreadable off-device.
- **File access via SAF**, so no storage permissions and any sync tool (Syncthing, rclone, etc.) owns the files.
- **Encrypted files are a separate implementation, not a mode of the plain one.** Its own read, its own write and its own cap, so crypto never gets threaded through the path that plain text uses and neither can quietly change how the other handles bytes. `readEncryptedDocument` and `writeEncryptedDocument` exist today only to fail with `NotSupported`.
- **An encrypted file is also laid out the old way: whole, in one text field, never in chunks.** Nothing about a plaintext should be inferable from how it is drawn, and a layout that measures only the part being looked at is one more thing that would have to be reasoned about before that could be claimed. Keeping the encrypted path on whole-document layout means there is nothing to reason about, and it costs only a cap: `MAX_ENCRYPTED_BYTES` is 128 KB, measured on the phone at 697 ms to lay out and about 800 ms from tap to text — under a second, with what is left of that second belonging to the key derivation. 256 KB was measured too, at 1.4 s, which is over the budget. In `DocumentState` this is the `whole` flag: one chunk covering everything, so the window covers everything and every edit is an ordinary edit in one field.
- **Dark mode is pure black, not Material's dark grey.** On an OLED panel a black pixel is an unlit pixel, so an editor that is mostly empty ground costs almost nothing to show. Every ground role in the dark scheme is taken to black — the greys Material picks are all elevation signals, and an editor with one toolbar and one text field has no elevation to signal. The foreground roles are left as the system chose them, dynamic colour included, so the accents still follow the phone's wallpaper; only what they sit on changes. The window background in `values-night` has to go black too, since that is what is on screen before Compose has drawn and a grey there flashes lit on the way in. Light mode keeps its own grounds. The one foreground either mode overrides is `outlineVariant`, which is what a divider draws itself with: Material's is a grey too faint to read against black or against white, so the rule under the toolbar is set to the plain opposite of its ground, white in the dark theme and black in the light one. That rule is one physical pixel rather than one dp, because on a dense screen a dp is nearly three pixels and at that width it stops being a line.
- **The window is cut again around the cursor on three triggers, and the third is the one that matters.** Near either edge is the obvious pair, and between them they answer deleting backwards and deleting forwards. The third is a ceiling on how much text the field may hold at all: text put into the *middle* of the window moves neither edge nearer the cursor, so nothing else would ever ask the window to move, and the field would go on holding everything pasted into it and laying all of it out again on every keystroke. That is the whole of why an editor gets slower the more has been pasted into it, and a ceiling is the whole of the fix.
- **What the view does when the window reaches backwards: it gives up the sliver of the top row that is already off screen, and nothing else moves.** The list finds its place again by the key of its top row, so a window that covered that row would leave it with nothing to find. Scrolling up by exactly the part of that row which is above the screen, plus one pixel, makes the row *before* it the one being held — and the window may then start there, because it is starting exactly where the anchor now is. Nothing jumps afterwards: the window draws that row's text at the same width in the same style, so it is the same pixels. **What makes the nudge small is that the cursor is kept on screen**, and that is a separate thing the editor has to do — see the next decision. Refused when the top row is scrolled so far off that the nudge would not be a nudge; the window then keeps the reach it has and gets the rest the moment an edit brings the cursor near its start.
- **Something has to scroll the cursor into view, and nothing was.** The field lays out inside a list item and the list is what scrolls, so neither of them knows where a cursor is. Deleting backwards is what shows it: the text below the cursor moves up and the cursor does not, so a long run of backspaces walks it off the top of the screen. Measured before it was answered: 1,904 backspaces left the cursor 37 lines above the viewport, and with it up there the window's reach backwards is refused for good, because the nudge above is only ever small while the cursor is near the top of the screen as well as near the start of the window. The two are one mechanism.
- **A selection that reaches outside the window is held as a mark over the document, not by the field.** Select-all on a gigabyte is not a thing a text field can hold, so the field goes on holding its few kilobytes with all of them selected, the rows draw the rest of the mark themselves, and the next edit made while the mark stands replaces the whole of it in the document rather than the run a diff would name. Nothing is decoded, laid out or copied to do it, so select-all costs the same on a gigabyte as on a line. The mark is dropped the moment the field's own selection stops being the whole of it, which is what a tap or a cursor move does.
- **Undo is the pieces a splice took out, and it lives with the splice.** A piece names bytes that never move, so remembering a change is remembering three or four objects and not one byte of text — restoring 44,615 bytes costs putting a list back. That is why it sits in `Pieces` rather than above it: it is the same fact from the other side. It is bounded by a count of changes rather than by their size, because size is not what would grow without end.
- **A save ends the history, and that is deliberate rather than a shortcut.** Saving re-opens the file it has just written and collapses the document back to one piece, which is what stops a long session accumulating; the changes remembered before that point name a descriptor that has been closed and a buffer that has been let go. Undoing past a save would mean keeping both alive, which is the thing the collapse exists to avoid.
- **Typing that carries straight on from what was typed last is the same piece, not another one.** Without that, a splice costs a piece per commit and every later splice walks all of them, which is an editor that gets slower the longer it has been open. With it, five hundred separate insertions at an advancing cursor are two pieces.
- **The buffer holding what was typed is append-only, so something has to let go of what nothing names any more.** Paste a megabyte, delete it, paste another: both are still in there, and only a save collapses them. Compaction is the answer and it has one subtlety worth writing down — the pieces the *remembered changes* are standing on have to be counted as still named, or walking one of them back would find its bytes somewhere else. It runs only once the buffer is large enough to matter and then not again until it has doubled, so a buffer that is all still in use is not copied over and over to learn that.
- **Everything under the last row is a tap target, and it belongs to the list rather than to the blank space at the end.** A spacer can only be as tall as it was made, so a document shorter than the screen — one just opened, and every new one — left the ground below it deaf, and the only way in was the one empty line at the top. The list is the thing that is always the size of the screen, so the tap goes on it: rows and the field each consume their own taps and a drag is consumed as a scroll, so what reaches the list is a tap that landed on nothing, which is exactly the case that wanted answering. Where it puts the cursor is the end of the document, which is what the spacer did and what tapping past the end of the text means anywhere else.
- **The window asking for focus is a question addressed to one window, and it is answered by the field actually being focused rather than by anyone taking the question.** Cutting the window again leaves two rows alive for a moment: the one being replaced re-runs its effects before the new one composes, and both are asking. A bare flag is taken by whichever runs first, which is the row about to be disposed, and it goes out with it — the field that survives is never focused, Compose ends its input session, and the keyboard shuts with no way back. So the ask names the window it is for, and a row left over from the last position does not match it. That is not enough on its own either: the row that does match can be disposed, or have its effect cancelled by the next cut, while it waits a frame for the layout — so what clears the ask is the field reporting that it holds focus, and until that happens the ask still stands for whoever composes next.

- **The information line keeps the type's own line height, and nothing about it is trimmed or clipped.** Two things were wanted from it and they point the same way: it should show what is actually there, and it should not move. A fixed line height is what stops it moving — it is a floor every script fits under, so the row is one height whatever is opened and the divider and the whole editor below it never jog. Trimming the leading off the top and bottom buys 16 px on Latin and then hands 8 of them back on Thai or Devanagari, because what is left after the trim is the font's own ascent and descent and that differs by script; a thinner row is not worth a row whose height depends on what language the file is named in. Not clipping is the other half: a combining mark that overflows its line is something the text really contains, and cutting it off would be the editor lying about its own content.

- **The activity takes configuration changes itself rather than being rebuilt**, rotation and a switch into dark mode included. A rebuild drops the open document, and nothing could bring it back: the descriptor the document reads through and the pieces standing on it are not something a saved instance state can hold, and no persistable permission is held that would let the file be opened again. That holds until there is somewhere to persist to, and even then re-opening a file loses unsaved edits, so it is the wrong answer for an editor.

## Environment

- **One UI publishes the phone's accent in the old palette resources and not in the new role ones, so Compose's dynamic colour misses it.** There are two sets: the `system_accent1_*` tonal ramp from API 31, and the colour roles API 34 added on top — `system_primary_dark`, `system_primary_light` and the rest. Compose reads the roles where they exist. One UI fills in only the ramp, leaving the roles at the AOSP default blue, so `dynamicDarkColorScheme` hands back a blue that has nothing to do with the phone. The accent is published and simply not looked at; reading the ramp and mapping the tones the way Material does gets it back. The neutrals are split the same way and nothing here is drawn in them, so they are left as they come. **`adb shell cmd overlay lookup <package> android:color/<name>` answers what a given app resolves a framework colour to**, which is how this was pinned down without a build — and it disagreeing with what the app draws is itself the finding.
- **The two decoders disagree about where the input buffer sits after a bad byte, and neither says so.** `CharsetDecoder`'s contract is that a malformed result leaves the input position pointing *at* the bytes it objected to, and a desktop JVM does that. Android's — ICU-backed — comes back already *past* them, while still reporting the run's length, so trusting either the position or the length skips a byte. The tell is a valid character disappearing from the screen right after a bad one: `C3 28` in UTF-8 shows as one replacement with the `(` gone. What works on both is to ignore the position entirely and work out where the good part ended from the characters it produced, since a strict decode is a bijection and the characters say exactly how many bytes they came from.
- **Android's decoder also reports a bad run that reaches past the first byte**, which matters more than it sounds: a file in some single-byte encoding is ordinary text with a bad byte every few words, and a run that swallows the byte after each one takes readable characters off the screen. Resuming one code unit past the error instead gives one replacement per byte that cannot be named and keeps every byte that can.
- **Lowering `WINDOW_MAX` to make the ceiling reachable does not give a smaller window, it gives an editor that cuts the window on every keystroke.** The window is whole chunks and never fewer than one, so it cannot be made smaller than about a chunk however low the ceiling is set. Put the ceiling under that and `tooLong` is true for ever: every change re-cuts, every re-cut disposes the row, and failures appear that no real ceiling can produce. Any ceiling worth testing with has to sit above the natural window, which is roughly three chunks — which is where the real one already is, so there is no useful room below it. Grow the document with real pastes instead and let the ceiling arrive on its own.
- **Samsung's Clipboard Manager panel closes itself whenever the field is disposed.** Re-cutting the window restarts Compose's input session, and the keyboard drops out of the panel back to the plain letters. A test that taps the same coordinate again then lands on whatever key is now there — a run of `3`s appeared in a document that was supposed to be receiving pastes — so the panel has to be re-opened before every paste, or at least checked for.
- **`uiautomator dump` cannot see the IME window at all**, so there is no way to read the keyboard's state, its panel or its buttons out of the accessibility tree; the dump contains only the app. What does work is reading the framebuffer directly: `adb exec-out screencap` with no `-p` gives a 16-byte header of width, height, format and colourspace followed by raw RGBA, so a handful of pixels can be sampled without decoding a PNG or needing any imaging library, which there are none of here.
- **`adb shell input keyevent 279` (KEYCODE_PASTE) does not reach the field**, the same way the movement keys do not, so there is no way to paste from the shell at all. The clipboard panel is the only route.
- **Asking for focus is not the same as raising the keyboard, and almost everywhere it looks like it is.** `requestFocus()` brings the IME up only where the field did not already hold focus. The window row is keyed on where it starts, so moving the window composes a new field, and a tap that moves the window therefore raises the keyboard — which is nearly every tap there is. The exception is a document of one empty line: the window never moves, so the field is the same field, and once the keyboard has been dismissed with Back the field still holds focus. A tap then puts the cursor back and leaves no keyboard under it, which reads exactly like the tap having been ignored. `LocalSoftwareKeyboardController.show()` alongside the focus request is what covers both, and it is a no-op whenever the keyboard is already up.
- **A synthetic tap at a y the keyboard covers types a letter.** Not an error, not a miss — `input tap` lands on the key that is there, so a tap meant for the blank space under a short document arrives as a character in the document instead. It looks precisely like the cursor having been put in the wrong place, since something did get typed at the wrong offset. With the keyboard up, the safe move is to check `mInputShown` before choosing a coordinate rather than after being surprised.
- **`adb shell input keyevent` reaches the field for editing keys and not for movement keys.** Backspace (67) and forward delete (112) both work, in batches of twenty-five codes per call, which is what makes it possible to drive the cursor around at all. The arrow keys, page down and move-to-end do nothing whatever — so the only way to walk a cursor is to delete with it. Everything below about the editor's edges was found that way.
- **`adb shell input text` is not a reliable way to type.** It splits on spaces, because the shell does — use `%s` — and it drops roughly half of a long string. What arrives, arrives correctly and in order, so it is fine for checking *what* an edit did and useless for checking *how much*.
- **The toolbar does not scroll any more, so its buttons are where they were last time.** It used to, and it cannot now: the buttons divide the width by weight, so there is nothing to scroll and no `HorizontalScrollView` in the dump at all. The whole button takes the tap and not just its word, so the centre of one is a safe coordinate with a good half-button of slack in either direction. Read the bounds off `uiautomator dump` all the same, because they move with the font scale — and because **which row is on screen depends on the keyboard**: the file row is not there while the IME is up.
- **The keyboard must be asked to resize and not left to the system, which picks per orientation.** With no `windowSoftInputMode` the activity is `adjustUnspecified`: portrait resized and landscape *panned*, and panning slides the whole window up to keep the cursor above the keyboard — which took the toolbar off the top of the screen and cut the file's name in half against the status bar. It looks like a layout bug and no amount of inset arithmetic can reach it, because the layout is correct and the window it is drawn in has moved. `adjustResize` in the manifest is the whole fix.
- **`safeDrawing` counts the IME, so padding a whole screen with it makes everything on that screen move when the keyboard opens.** Anything sized off what is left of the screen — a row whose height is a fraction of the shorter edge, say — then shrinks as the keyboard rises. The split that works is for the column to pay the top and the sides and for whatever sits against the keyboard to pay the bottom, IME included, on its own.
- **Taps sent back to back in one shell command are unreliable.** Two or three `adb shell input tap` calls in a row, or a tap followed immediately by a `logcat` read, regularly show nothing having happened; the same tap on its own works. Whatever is being coalesced, the fix is to send one tap per call and to put something slow — a `uiautomator dump` — between the tap and the read.
- **`adb shell input keyevent` can deliver more codes than it was given.** 100 calls of twenty-five forward deletes took 2,906 characters out, not 2,500. Fine for driving the editor, useless for counting — take the count from the app, not from what was sent.
- **The shell here cannot touch the clipboard.** `cmd clipboard` answers `No shell command implementation`, so there is no way to test a paste except by hand.
- **`am start` at an app that is already running does not restart it**, so the intent's file is never read and whatever was on screen — including a dialog — is still there, which reads exactly like the app ignoring the test. `adb shell am force-stop com.lucasta.edit.debug` first.
- **The phone locking mid-run looks exactly like the app ignoring the test.** Injected input goes nowhere, `uiautomator dump` returns the lock screen, and the app is fine — so a run that suddenly stops responding is worth checking `dumpsys power | grep mWakefulness` on before concluding anything about the code.
- **`file://` URIs work for testing refusals.** `am start -d file:///dev/null` and `-d file:///sdcard/Download` both reach `openFileDescriptor`, which is a way to point the app at something that is not a regular file without needing a provider that streams.
- **A URI permission granted by an intent belongs to the file, not to the name.** Replace the file underneath and the grant is gone with it, and saving fails with `has no access to` even though nothing about the app changed.

Everything below is plain `pkg install` or a stock SDK — no hand-assembled pieces, no version fictions, nothing that needs to be worked around.

- **Kotlin daemons do pile up.** A build warned `Detected multiple Kotlin daemon sessions` and two `KotlinCompileDaemon` processes were alive at once, each with its own 2 GB ceiling and `--daemon-autoshutdownIdleSeconds=7200` keeping it around for two hours. Worth clearing between sessions: `gradle --stop` handles the Gradle daemon, the Kotlin ones need `pkill -f 'KotlinCompileDaemo[n]'`. Write the pattern with a bracket like that, because a plain `pkill -f KotlinCompileDaemon` also matches the shell running it and kills the command itself — that shows up as exit code 144 out of nowhere.
- **Opening a big file used to be a memory event and no longer is.** Before the model landed, at the old 32 MB cap the app was 257 MB of RSS and opening 32 and 64 MB files repeatedly with the daemons alive got the low-memory killer to cull everything, terminal included. Now a gigabyte open is 143 MB of PSS and 9 MB of heap, and opening one with both daemons running did nothing at all. Building is still the risk, not opening. What survives a cull is everything on disk; what dies is the daemons and the adb server.
- **`pkill -f 'KotlinCompileDaemo[n]'` still kills your own shell if the name appears anywhere else on the command line.** The bracket protects the pattern, not a second literal mention of it later in the same line — a `pgrep -af "KotlinCompileDaemon"` in the same command is enough to bring back exit code 144.
- **A build is two JVMs with 2 GB heap ceilings each.** The Gradle daemon runs `-Xmx2048m` and the Kotlin daemon another `-Xmx2048m` (with `--daemon-autoshutdownIdleSeconds=7200`, so it lingers long after it is done compiling). That is 4 GB of ceiling on a phone with far less than that free. It is worth knowing but it is no longer the thing to work around: none of the ideas once filed here — killing the Kotlin daemon between phases, `--no-daemon`, capping `org.gradle.jvmargs` — were needed.
- **Lint has to be asked for, and costs 13 minutes.** `assembleDebug` does not run it and `lint { checkReleaseBuilds = false }` disables the release hook, so nothing in the normal flow ever checks. `gradle lintDebug` works — 13m 5s cold, no OOM, so it is safe to run unlike release — and writes `app/build/reports/lint-results-debug.{html,sarif}`. It prints nothing useful to the console; read the SARIF. Worth running occasionally rather than never, but not per change.
- Gradle 9.7.0 comes from `pkg install gradle` — the same version `gradle-wrapper.properties` pins. `gradlew` is still in the repo and correct for anyone else, but the wrapper distribution was never downloaded here, so `./gradlew` would pull 130 MB from `services.gradle.org` to arrive at the same Gradle. The termux mirror runs about 10x faster than Google's, which is why the packaged one won.
- JDK is `openjdk-21` (21.0.12). AGP compiles to JVM 17 bytecode regardless, per `compileOptions` and the `kotlin` block.
- **aapt2 is `pkg install aapt2`**, a native aarch64 build reporting `2.20-android-16.0.0_r4` — genuinely build-tools 36 era, which is what AGP 9 expects. `optimizeReleaseResources` runs and produces a correct APK, so the old `android.enableResourceOptimizations=false` workaround is gone.
- The one setting that has to stay is `android.aapt2FromMavenOverride`, pointing at `/data/data/com.termux/files/usr/bin/aapt2`. AGP's own aapt2 comes from Maven as a glibc x86_64 binary that cannot run under bionic, so without the override every build dies in `processDebugResources`. It lives in `~/.gradle/gradle.properties`, not in the repo, because it is an absolute path for this machine only.
- **SDK is at `~/android-sdk`, installed by a real `sdkmanager`** (cmdline-tools 22.0). `local.properties` points at it, so no `ANDROID_HOME` is needed. The cmdline-tools scripts ship a `#!/usr/bin/env` shebang that termux cannot resolve; `termux-fix-shebang` on `cmdline-tools/latest/bin/*` fixes it once.
- `platforms;android-37.0` is installed properly, with `package.xml`. `compileSdk = 37` resolves to `android-37.0` specifically — `android-37.1`, the Android 17 minor release, does not satisfy it.
- **AGP auto-installs `build-tools;36.0.0` and `platform-tools`, and both are x86_64.** Nothing executes them: aapt2 comes from the override and D8, R8 and apksigner are JVM tools. The debug build in fact succeeded before build-tools existed at all. Worth remembering only if some future AGP task shells out to a native build-tools binary, which would fail with an exec format error.
- **Nothing installs an APK from the termux shell except adb.** Four routes were tried and each is walled off differently. `pm install` fails because SELinux denies `system_server` access to `app_data_file`, so it cannot read the build dir; it suggests `/data/local/tmp`, which an app uid cannot write to. `content query`, which would get a MediaStore URI the way a file manager does, needs the privileged `ACCESS_CONTENT_PROVIDERS_EXTERNALLY`. `am start` is refused because it identifies as `com.android.shell` while running as our uid, so `assertPackageMatchesCallingUid` throws. `termux-open` does raise the install prompt — Termux has "install unknown apps" granted — but the installer rejects its FileProvider URI, with or without an explicit `--content-type`, and whether the APK sits in the build dir or in `~/storage/downloads`. The installer only accepts a `content://` URI, Termux's provider is the one it refuses, and every tool that could mint an acceptable URI needs a privileged permission.
- **adb is paired and this is now the way we install.** `pkg install android-tools`, a native aarch64 build. `adb install -r app/build/outputs/apk/release/app-release.apk` streams the APK over a socket rather than handing over a path or a URI, so none of the walls above apply and it works straight from the build dir with no copying and no tapping. `adb shell am start -n com.lucasta.edit/.MainActivity` launches it, and `adb logcat` finally gives us crash output.
- **Reconnecting after a reboot or a Wireless debugging toggle.** Pairing itself survives, but the connect port changes every time, so it needs `adb connect 127.0.0.1:<connect-port>` with the port read off the main Wireless debugging screen. **Use the loopback address and not the LAN one.** Both adb and the phone are the same machine, so `127.0.0.1` always reaches it; the LAN address on that screen is only correct while the phone is on the network it was noted from, and when it is not, `adb connect` fails with `No route to host`, which reads like the port having changed and is not. That screen is not a popup, so it can be read after switching apps. This adb has no mDNS support, so `adb mdns services` errors out and the port cannot be discovered automatically. The adb server also dies on its own between commands here — when a command reports `daemon not running; starting now` and then `no devices/emulators found`, the fix is just `adb connect` again on the same port, which is still valid. Cheap enough to prefix onto any adb command after a gap. **After an OOM kill the server comes back wedged, and `adb connect` alone will not fix it** — it reports success or silence and `adb devices` still lists nothing. `adb kill-server` then `adb start-server` then `adb connect` recovers it on the same port. Do not conclude from a failed `adb connect` that the port changed; check with a server restart first, because reading a new port off the phone needs the user.
- **Pairing again, if it is ever needed, requires split screen.** Android invalidates the pairing session the instant the pairing dialog is dismissed, and switching apps dismisses it — so the code can never be relayed by switching to the terminal. What that failure looks like is `error: protocol fault (couldn't read status message)`, which reads like a broken adb and is not one; the termux issue for it is closed as not-bug. Put Settings and the terminal side by side in split screen, then run `adb pair <ip>:<pair-port> <code>` while the dialog is still on screen. The pairing port and the connect port are different.
- Falling back without adb means `cp` to `~/storage/downloads` and tapping the file by hand in a file manager.

## Known limits of the current editor

Numbering follows what was there before, so a limit that was fixed is struck rather than renumbered.

1. ~~Only files that survive a byte-exact round trip open at all.~~ Fixed by byte addressing: a file with bad bytes in it opens, shows one replacement character per byte that cannot be named, and saving copies every byte nobody touched out exactly as it came in.
2. ~~Legacy single-byte encodings are rejected.~~ Same fix. A Latin-1 file opens and every ASCII character in it is readable; the accented bytes show as replacements and survive a save untouched. It is not *decoded* as Latin-1 — nothing detects that — so those characters cannot be read or edited, only preserved.
3. No unsaved-changes tracking, so opening a second file, or starting a new one, silently throws away edits to the first. Cheap to answer now: a document that has never been edited has one piece and an empty typed buffer.
4. ~~The whole file is read into one String.~~ Gone with the model.
5. No persistable URI permission is taken, so a file cannot be reopened after the process dies. Harmless until there is a recent-files list to reopen from.
6. **Save fails outright when the app was handed read-only access**, with `could not save: <package> has no access to <uri>`, which is accurate and useless. It should fall back to offering Save as, since that is the actual way out — and the Save as branch the collision dialog already has is the same one. This also shows up after a file is replaced under an open document: the grant that came with the intent belongs to the file that was there, so it is gone along with it.
7. **A drag-selection cannot cross the window's edges.** About a hundred lines of reach. Nothing else has this limit any more: editing crosses them because the window moves, and select-all crosses them because it is a mark over the document rather than a selection in the field. Find and replace will be the same when it exists. What is left is the gesture itself, which is Compose's and belongs to one field.
8. **Scrolling away from the cursor closes the keyboard**, because the window row is a `LazyColumn` item and scrolling it off screen disposes it. The cursor and the edit survive; only the focus does not.
9. ~~Typing thousands of characters grows the window instead of moving it.~~ Fixed by the ceiling on how much the field may hold, which is the third of the three triggers under the design decisions. Verified by lowering the ceiling to make it reachable from `adb shell input text`, which is too lossy to type sixteen thousand characters: the field was cut back from over the ceiling to 2,910 characters with the cursor at 982, nowhere near either edge, and 2,850 typed bytes came out of the save at the right offset with nothing else moved.
10. An edit shifts the offsets of every chunk after it, and the list is keyed on those offsets, so the scroll position can jump by a row or two when a window is committed while its neighbours are on screen.
11. **Tap into the last visible line of a row that is mostly scrolled off the top, and the window still has no reach backwards.** The nudge that makes room for it is the part of the top row already above the screen, and there that part is most of a screen, so it is refused rather than thrown. It costs nothing in practice: the reach arrives on the first edit that brings the cursor near the window's start, because by then the cursor is being kept near the top of the screen too. Everywhere else the reach works — verified by tap and by 1,904 backspaces.
12. ~~The window never actually follows the cursor, so an edit is confined to the four kilobytes it opened in.~~ Fixed, in three parts that had to arrive together: the window is consulted on every change to the field and not only on every move of the cursor, so deleting forwards reaches it at all; the cursor is scrolled into view, without which it walks off the top of the screen while deleting backwards; and the nudge gives the list's top row away so the window may cover it. See the design decisions for each. Verified on the phone by backspacing 2,900 characters through two window starts and by 2,906 forward deletes through the far edge.
14. ~~A commit whose edit starts exactly where the top visible row starts pushes `visibleFrom` past the whole insertion.~~ Fixed: the anchor now has to be strictly past the edit's start as well as at or past its end, since an insertion has `to` equal to its own start and text inserted at the top row's start belongs to that row rather than above it. The undo path carried the same edge case — `span.was` is 0 for an insertion — and got the same guard. It never reached anything written: `visibleFrom` is view state and never an edit coordinate, so the cost was a wasted window cut and the two live rows that came with it.
13. **A second file opened by intent while the app is already running does nothing**, because there is no `onNewIntent` and the URI is only read in `onCreate`.
15. **A glyph that draws outside its line draws over whatever is beside it, and nothing clips it.** Stacked combining marks — the Zalgo trick — climb over the row of buttons above the information line and hang through the divider into the document's first line. The row does not grow to fit them, because a line is measured from the font's metrics and marks like these do not change the metrics; they simply paint outside. Compose is what makes it visible: a `Column` does not clip its children, where an Android `ViewGroup` clips by default, so what would have been cut off on a `TextView` is drawn here. Accepted deliberately — see the design decision — and worth knowing before it is mistaken for a layout bug. Thai and Devanagari stacks escape too but land in empty space; emoji do not escape at all. The same is true of the document's own rows, where a file full of marks will bleed between them.

## How the text is laid out

- **There is no buffer.** The document is a sequence of pieces over two places — ranges of the open file, and ranges of an append-only buffer holding what has been typed — and an edit rewrites the sequence rather than any bytes. What is in memory measures the editing and not the file: a gigabyte open costs about nine megabytes of heap.
- **Chunks.** `Chunks.kt` indexes the document into chunk starts of about 2 KB, cutting on line breaks so a chunk boundary falls where a line break already is and wrapping inside a chunk is what wrapping the whole document would have produced. A line with no break in it is cut at a space, which is the only place a boundary is visible, and never in the middle of a character. The index is an `IntArray` of byte offsets — no boxing anywhere — built off the main thread for documents over `INDEX_OFF_THREAD` (256 KB) and inline below that, where the hop off the main thread and back costs more than the scan. After an edit only the chunks the change fell inside are indexed again (`respan`); the span is widened to whole chunks first, or re-indexing from where the typing happened to start would put a boundary in the middle of a line.
- **Reading a run of the document allocates a fresh array every time**, so indexing a file allocates it once over in 64 KB pieces — 128 MB of short-lived garbage for a 128 MB file — and every row drawn allocates its couple of kilobytes. It never shows up in the process size, which stays flat, but it is the obvious thing to hand a reusable buffer to if indexing is ever made incremental, since that turns one burst of garbage into a steady trickle.
- **The scan is over bytes, and both size targets are scaled by the size of a code unit**, so a chunk holds about as much text whatever the file is written in. Reading raw bytes out of a `ByteArray` is fast interpreted and hot enough to be compiled — a window is 64 KB, tens of thousands of iterations per call — so the trick the old character scan needed, copying into a String to reach `String.indexOf`, is not needed here.
- **Rows.** `DocumentEditor` is a `LazyColumn` of chunks, so only the chunks on screen are ever measured and scrolling recycles them. A row's text is decoded when it is drawn and thrown away when it scrolls off. Fling and jump-to-anywhere come from `LazyColumn` for free. **Which rows there are is worked out from the chunk index rather than held as a list of rows**: a list is one object per chunk built again on every edit, and a chunk is two kilobytes, so on a large document that was hundreds of thousands of objects and megabytes of garbage per commit for an answer that is two comparisons and an addition.
- **The window.** One slice of the document — the chunk the cursor is in plus `WINDOW_CHUNKS` either side, about 6 KB — is a real `BasicTextField` and takes all the input, so IME, selection handles, magnifier and autocorrect are Compose's and not ours. Every other row is read-only `BasicText` that turns into the window when tapped. It follows the cursor: come within `WINDOW_GUARD` characters of an edge, or put more than `WINDOW_MAX` into it, and what changed is committed and it is cut again around the cursor. It is consulted on every change to the field rather than on every move of the cursor, which is the only way deleting forwards or pasting could ever reach it.
- **What the window commits is the run the typing actually touched, not the whole window.** A window is a few thousand bytes of which almost none was typed, and committing all of it would fill the typed buffer with text nobody typed and leave the file's own bytes for that run behind, which is exactly what byte pieces exist to avoid. It also means the window doubles as an edit coalescer: a piece is created per commit, not per keystroke.
- **Encrypted documents opt out of all of it.** `load(whole = true)` gives the document a single chunk, so the window is the whole file and the layout is exactly what it was before chunking existed. See the design decisions for why.
- **The list holds its place by the key of the row at the top of the screen, so the window may never start above that row** — a row the window covers stops being a row, and the list then falls back on row numbers, which mean somewhere else once the window has collapsed a few rows here and given a few back there. That was the jump when tapping after a long scroll.
- **`WINDOW_CHUNKS` is the dial.** The window is the only text a keystroke lays out again, so raising it buys a longer drag-selection and costs typing latency, at roughly 4 µs per character of window. Nobody has measured typing latency yet.

## Speed of opening

Measured after the model landed, driven by `adb shell am start -a android.intent.action.VIEW -d content://media/external/file/<id> --grant-read-uri-permission -n com.lucasta.edit.debug/com.lucasta.edit.MainActivity`, timings from `adb logcat -s edit.perf` (the `timed`/`frameAfterNext`/`heap` helpers in `Document.kt`, temporary). MediaStore ids come from `adb shell content query --uri content://media/external/file --projection _id:_display_name`.

| file | index | total open | first frame | heap after | process PSS |
| --- | --- | --- | --- | --- | --- |
| 32 MB | 165 ms | 234 ms | 75 ms | 11 MB | 124 MB |
| 64 MB | 276 ms | 289 ms | 63 ms | 8 MB | 119 MB |
| 128 MB | 520 ms | 538 ms | 53 ms | 12 MB | 120 MB |
| 1 GB | 4767 ms | 4820 ms | 171 ms | 9 MB | 143 MB |

**Reading is gone from the open path entirely** — nothing is read but the first 64 KB and whatever the index scans — and what is left is the index, flat at about 4.7 ms per MB. For comparison, before this the same 32 MB took 999-1052 ms and 202 MB of PSS, and 64 MB could not be opened at all. **Both the heap and the process are now flat in the size of the file**: about 120 MB of PSS is what this app costs with nothing open, and a gigabyte adds twenty.

Before chunking existed, laying out the text was linear at roughly 5 seconds per MB — 64 KB 252 ms, 1 MB 5.2 s, 4 MB an ANR with 1.1 GB resident — and a plain `EditText` behind `AndroidView` ANR'd at 4 MB too, so it was never about which widget.

Do not read `setText` in the log as the cost of the index: it is a suspend call, so on documents over 256 KB it is the index plus however long the main thread took to get back to the continuation, which during app startup is most of it. A first launch after an install runs about twice as slow across the board, so take the second run.

**The index is the last whole-file pass, and making it incremental is the next thing worth doing.** Index the first stretch, show the rows there are, and continue behind the list: the row count a `LazyColumn` insists on is a count, not the final count, and rows appended at the end do not disturb where anyone is looking. That is what would take a gigabyte from five seconds of nothing-on-screen to about as fast as anything else. What it has to handle is an edit landing while the tail is still being indexed — the offsets after it move — which is why the batch wants a generation stamp and a restart rather than a merge.

## File size

State: two caps, both refused with our own message — `MAX_FILE_BYTES`, now the whole of what an `Int` can address, for plain files, and 128 KB for encrypted ones (`MAX_ENCRYPTED_BYTES`, see the design decisions). The format is sniffed from the first bytes before the size is checked against that format's cap, so a 292 KB file opens as text and is refused as an encrypted file. The size comes from `fstat` on our own descriptor rather than from a provider column, so there is no second opinion to be wrong.

**Nothing in memory scales with the file any more.** The heap holds the chunk index, the pieces, whatever has been typed, and the one slice the window is showing. The index is the only one of those that grows with the file, at four bytes per two kilobytes — one part in five hundred, so 2 MB for a gigabyte.

What is left is:

1. **`Int` addressing**, which is the cap. Every offset in the document, the index and the pieces is an `Int`, so 2 GB is the ceiling and the cap is set at it. Going past it means `Long` offsets through all four pure files, and it buys files this app almost certainly should not be opening.
2. **Patience with the index**, which is what actually bites first — about 4.7 ms per MB, so a gigabyte is five seconds with nothing on screen. Incremental indexing is the answer and is not written yet.
3. **The temporary a save writes**, which costs the document's size in app storage while the save runs, plus the same again copied over the file.

**None of this is per-device any more.** The old cap was a number chosen against one device's 256 MB heap and was wrong on other hardware in both directions. Nothing here depends on the heap the device hands out.

`edit-test-{064,128,256}kb.txt`, `edit-test-{001,004,016,032,064,128}mb.txt` and `edit-test-1gb.txt` are the files to check it with, plus `edit-test-fake-{small,big}.age`, which are not encrypted at all — they just start with age's magic, which is all `looksEncrypted` looks at — and `edit-test-{utf8,utf16le,malformed,latin1}.txt` for the decoder. `edit-test-window.txt` (1,000 numbered lines of 51 bytes) and `edit-test-save.txt` (300 of the same) are what the window was driven with: every line says where it is, so a screenshot says where the window is and a common-prefix comparison says exactly which lines an edit took out. Regenerate them rather than reusing one that has been edited. New files in shared storage are invisible to the app until MediaStore knows about them: `adb shell content call --uri content://media/external --method scan_file --arg /sdcard/Download/<name>`.

## Verified on the phone

Everything below was checked on the phone after the model landed, not reasoned about. Status text read with `adb shell uiautomator dump /sdcard/ui.xml` — Compose publishes its text to the accessibility tree, which is far cheaper than screenshots and gives the exact string. Files were compared by pulling them and finding the common prefix and suffix, which says exactly what changed and exactly what did not.

**Opening.** UTF-8 with multibyte content and UTF-16LE with a BOM both open and render, the BOM stripped. A Latin-1 file opens with one replacement character per accented byte and every ASCII character around it readable. A file with a bad byte opens as `good text here` / `�( bad byte` / `more text` — the `(` after the bad byte survives, which is the whole point of the decoder note below. Both caps refuse with the right message and the right limit. A 1 GB file opens.

**Saving.** A save with no edits at all is byte-identical. Editing and saving inserts exactly what was typed and changes nothing else: 7 bytes at offset 39 of a UTF-8 file with the other 4,908 identical; 18 bytes in a UTF-16LE file, correctly two bytes per character, with the BOM kept and everything else identical; `XX` into the Latin-1 file with both bytes no decoder can name still there afterwards; and 7 bytes at offset 13 of a 32 MB file, checked by rebuilding the expected file on the phone with `head -c`/`tail -c +` and comparing sha256, which matched. Two edits with a save between them both land, which is the re-open after a save working.

**Collisions.** With a document open, replacing the file underneath — write a temporary, rename over it — brings up the dialog with Overwrite, Save as and Cancel. While a completely different file sat at that name, the app went on showing and reading the original through its descriptor, which is the snapshot doing exactly what it is for. Rewriting the same file in place instead is refused with `<name> was rewritten while it was open, so this document is no longer all of it`.

**Editing.** Tap places the cursor and the tapped character is the one it lands on. Typing works, Enter works, and a new empty document takes typing straight away. 1,554 characters typed in one go into a 4 MB file landed as one contiguous run at one offset with the other 4 MB identical. Long press selects the word under it and typing replaces exactly that word, checked across a run of CJK where nine bytes went out and four came in with nothing else moving. Tapping the blank space under the last line puts the cursor at the end of the text and *before* the file's final line break, so typing there extends the last line and the trailing newline survives — which is right, and is the trailing break the window deliberately does not hold.

**Save as.** The system picker opens, offers the document's name, and creating a file writes to it; the document then follows the new file, and a later Save goes there and carries every earlier edit with it. Back out of the picker and nothing is written and nothing is lost.

**Refusals.** A character device (`file:///dev/null`) and a directory are both refused with `it arrives as a stream, not as a file`, which is the seekability check.

**The release build.** It installs and launches with nothing but launcher noise in the log. Editing and saving through it is byte-exact — eleven bytes in at offset 39 of a UTF-8 file, everything else identical — so R8 has not quietly broken the model, which was the thing worth checking. It opens the 128 MB file in 700 ms at 66 MB of process, about half what the debug build costs for the same file.

The window following, undo and select-all, on the phone, driven by taps and by `adb shell input keyevent` and read back from `adb logcat` with temporary traces in `open`, `reach`, the mark and undo. Files were compared by pulling them and finding the common prefix and suffix, which says exactly what changed and exactly what did not.

**The window reaching backwards.** Tapping into the first lines of the window row moved it from 10455..16728 to 8364..14637 after a 202-pixel nudge, and the screen showed the same text either side of the move. Backspacing did it too, twice in a row, at 4182..8364 → 2091..7028 and then → 0..4885, at 233 and 89 pixels of nudge. The refusal case is real and harmless: one recut in the middle of a run was declined because the top row was scrolled too far off, and the next one a second later took it.

**The window reaching forwards.** 2,906 forward deletes were absorbed and the far edge moved with them, which is the case that was measured earlier never to be consulted at all.

**Select-all.** On a 44,615-byte document, typing one character over it left the document holding exactly that one character, and backspace over it left it empty — both in one splice, `0..44615`, with nothing decoded. The mark is drawn across the read-only rows as well as inside the field, so the whole document looks selected.

**Undo and redo.** Four runs of deletion walked back one at a time to exactly 51,000 bytes and forward again to exactly 44,615, the same offsets and lengths in both directions. Undoing a whole-document replacement put all 44,615 bytes back from one character. Select-all, delete everything, undo, save gave a file with the same sha256 as the one that was opened.

**Saving.** A save with no edits is byte-identical. Select-all and type saved as exactly the five bytes typed. A 2,850-byte run typed across several window recuts came out as one insertion at offset 162 with the other 15,138 bytes untouched.

**Large files still open and edit.** The 128 MB file opens in 834 ms of indexing at 141 MB of process, scrolls, takes a tap and deletes eight characters exactly where the cursor was.

**Tapping the ground under the text.** On a freshly started app — an empty document, nothing focused — a tap far below both the one empty line and the spacer put the cursor on that line and raised the keyboard, and typing landed in the field. Dismissing the keyboard with Back and tapping the ground again brought it back, which is the case where the field never lost focus and `requestFocus` alone did nothing. Same after New, and after New the ground tap took typing straight away. On a document with text in it the ground tap puts the cursor at the end: with the cursor sitting at offset 2, a tap on the ground and one character came out at the end of the line.

**What the ground tap did not take.** A swipe still scrolls — 1,100 pixels moved the list from line-0000 to line-0014 — and a tap on a read-only row still lands where it was aimed, `ZZ` typed six characters into line-0020 with the rest of the row untouched. Both matter because the handler sits on the list, above every row: rows and the field consume their taps before it sees them, and a drag is consumed as a scroll.

**Pasting repeatedly no longer shuts the keyboard.** 120 real pastes from the clipboard panel into a new document, checking `mInputShown` after every one: none closed it. The re-cuts in that run show the mechanism working — the row left over at the window's old start is refused, the row drawing the new start is granted, and the field then reports itself focused. Before the fix the same point closed the keyboard for good; it only came back because a later paste happened to raise it again. Read `mInputShown` out of `dumpsys input_method` rather than trusting a screenshot, since the panel and the keyboard look alike at a glance.

## Not started

- **Incremental indexing.** See the end of "Speed of opening". The largest remaining win and the last whole-file pass.
- Editor UI: find and replace, a scrollbar or some sense of where in the file you are. Find is the next one worth doing and it is now cheap to place: it works on the document, it can put the answer under the window the way a tap does, and the mark that select-all uses is already the way to show a match that is off screen.
- Unsaved-changes tracking, which limit 3 wants and which the piece list makes nearly free — and which the change list now makes exact rather than nearly free, since a document that has never been changed has nothing to walk back
- Save as as the fallback when saving is refused, which limit 6 wants
- Encryption: passphrase entry, KDF, envelope format, decrypt-on-open / encrypt-on-close. The split is in place, `EncryptedFile.kt` is where it goes, and the magics it sniffs are age's only provisionally.
- Device-to-device backup posture. `allowBackup="false"` stops cloud backup on every supported version, but from Android 12 it does not stop device-to-device transfer — that needs `android:dataExtractionRules` with a `<device-transfer>` exclude, which costs an XML file. The app persists nothing at all today, so there is nothing to leak; do this when it first stores something, such as recent files, SAF permission grants or settings.
