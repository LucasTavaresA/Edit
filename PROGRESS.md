# PROGRESS

Progress tracker for **Edit** — a bare text editor for Android that opens and closes encrypted files in a format any tool can read and sync.

## Where the project stands

A working bare editor: open a file, edit it, save it, undo it. The document is the file where it lies plus a list of the changes made to it, the window you are typing follows the cursor wherever it goes, how much can be edited in one place is not a question at all. There is only one undo history that answers for everything.

- Some files are pure Kotlin with no Android in them, and they are where a mistake can corrupt a file: `Encoding.kt` (what a file is written in, and the arithmetic that follows), `Pieces.kt` (the sequence of pieces, the splice, the changes made to it and the compaction of what was typed), `Chunks.kt` (the chunk index over bytes) and `Slice.kt` (decoding a run for the screen, and the map back). The other six are the Android side: `Content.kt` (the open descriptor and the document built on it), `Document.kt` (vocabulary, caps, open and save dispatch, the collision check), `TextFile.kt` (the plain path), `EncryptedFile.kt` (stubs), `Editor.kt` (`DocumentState` and the composables) and `MainActivity.kt` (theming, toolbar, wiring). The theme is a handful of lines inline in `onCreate`, not its own file or package.
- No tests and no test dependencies. No crypto code yet.

## Design decisions

- **The document is the file plus its changes, and it behaves as a whole copy of the file taken the instant it was opened.** What a save writes is that copy with our edits in it and not one byte from anywhere else — never something another tool put there in the meantime, whether it appended, rewrote or replaced. The change list is only how a copy that large is afforded.
- **Crossing between characters and bytes is arithmetic, not a table.** A strict decode is a bijection, so what a run of characters weighs in bytes can be counted without encoding it, and the map a slice carries has an entry only where the decoding was *not* a bijection — one per byte the encoding could not name. Ordinary text carries no entries at all, whatever it is written in. What makes that safe is that the arithmetic has to agree with the encoder on *every* input and not only on well-formed input, unpaired surrogates included.
- **A file that does not decode is opened anyway, and that is now the default rather than a deliberate choice.** The old refusal existed because the whole file was decoded on the way in and re-encoded on the way out, which made every byte the decoder could not name a byte that saving would destroy. Under byte addressing that is no longer true, so a file with a few bad bytes in it, or one in a single-byte encoding nobody can detect, opens and reads and is safe to edit somewhere else. What refuses a file instead is one zero code unit in its first 64 KB: text does not contain one and everything that is not text is full of them, and it is a rule about the file rather than about the decoder.
- **A file we cannot seek in is not opened, and this is settled.** Every provider backed by a real file on the phone gives a seekable descriptor, which is every file this app exists for; the ones that stream their content instead are refused with a message, since a save writes the file as it was when opened plus the tracked edits.
- **The open descriptor is the snapshot, so nothing is copied and opening stays fast.** A descriptor pins the file it was opened on, not the name: a tool that replaces the file — writing a temporary and renaming over it, which is what Syncthing and rclone do — leaves what we are reading alive and intact until we close it, whatever the name now points at. That is a real snapshot for the price of holding one descriptor. The bytes stay on disk rather than in memory, so it costs the space of the replaced file until the document is closed.
- **A tool that writes in place is the case a descriptor cannot cover, and it is `fstat` that catches it, not a hash.** Size and modification time read back off our own descriptor say so for nothing — where a hash costs a full read of the file to learn the same thing, and could still only ever say that bytes are gone, never bring them back. So it is refused with a message and the document is not silently half old and half new. The time is read to the nanosecond, which leaves the clock the filesystem stamps writes with, a few milliseconds, as the only blind spot: a tool that rewrites in place within one tick of the open, without changing the size, would not be caught. Before API 27 there are only whole seconds. What nothing catches is a tool writing into the file while a save is copying into it, since nothing on a phone makes another app wait: both writes land, and the save only notices if the other one finishes after it.
- **A save onto a file that changed since it was opened asks first: overwrite, save as, or cancel.** This is the ordinary collision — sync brought a newer version while the document was open — and the document itself is fine, since the descriptor kept it; the only question is whose version the file ends up holding, and that is the user's to answer, not ours. Device and inode taken at open are what the question is asked from, which is the exact test for "replaced" rather than a guess from size and time.
- **Saving is the one place a copy is unavoidable, and afterwards the document starts again from what was written.** Writing through SAF truncates the file our own pieces still point into, so the output goes to a temporary in the app's storage and is copied over the file afterwards. That is two passes for a save and the file's size in space while it runs, and it buys back that the file is only touched once there is a whole document to put in it. **The look that decides a save is taken once the descriptor it writes with is open and the temporary is finished.** The document's own descriptor has to be as it was, or the temporary may hold somebody else's bytes, and the file has to be the one the document was last in step with, exactly as it was left. A descriptor writes into the file it was opened on and not into the name, so nothing that replaces the file after that look can be written over. The write descriptor is only asked which file it is, by inode; how that file stands is asked of a fresh read, since the write descriptor can report its own device and time (see the environment). The document then re-opens the file it just wrote and collapses back to one piece, but only if the re-open finds the very file that was written, at the size it was written to. Anything else means something replaced the file or wrote into it while the copy ran: the document keeps the temporary as its snapshot instead, unlinked, leaves the file unstamped, and the save asks the collision question there and then rather than saying it saved.
- **Opening, saving and New take turns, and however fast Save is pressed the file ends up holding everything up to the last press.** A save writes in place into the very file the document's descriptor is open on, so whatever reads the document while a save runs is reading a file halfway through being rewritten. A second save would copy that into the file and say "saved"; a collision check made meanwhile takes our own write for somebody else's and warns or asks. Opening a file or New closes the descriptor a save is reading through. So they run one at a time, in the order they were asked for, and the check before a save is part of the same operation as the write. The turns are the process's and not one screen's, so a second copy of Edit takes turns with the first — but nothing is refused and no button goes off while one runs: whatever is asked for meanwhile waits its turn. A save writes the document, and to the file, as they stand when its turn comes rather than when Save was pressed, so a press while a save is already waiting joins it, and a save that finds nothing changed since the file last held the document writes nothing. A save that has started is never cut short, since stopping one partway through the copy leaves the file neither version.
- **The encrypted path keeps its own model** — decrypted whole, in memory, never a byte of plaintext on disk. It is the same `Content` with every piece pointing at the typed buffer and none at a file. No pieces into a file, and nothing written anywhere, temporaries included, that is not ciphertext.
- **Encryption format must be tool-agnostic.** A single self-contained file (age, or AES-GCM + Argon2id envelope) that any desktop tool can decrypt. Explicitly NOT Jetpack Security / `EncryptedFile` — it binds keys to the device keystore, making files unreadable off-device.
- **File access via SAF**, so no storage permissions and any sync tool (Syncthing, rclone, etc.) owns the files.
- **Encrypted files are a separate implementation, not a mode of the plain one.** Its own read, its own write and its own cap, so crypto never gets threaded through the path that plain text uses and neither can quietly change how the other handles bytes. `readEncryptedDocument` and `writeEncryptedDocument` exist today only to fail with `NotSupported`.
- **An encrypted file is also laid out the old way: whole, in one text field, never in chunks.** Nothing about a plaintext should be inferable from how it is drawn, and a layout that measures only the part being looked at is one more thing that would have to be reasoned about before that could be claimed. Keeping the encrypted path on whole-document layout means there is nothing to reason about, and it costs only a cap: `MAX_ENCRYPTED_BYTES` is 128 KB, which lays out in about 700 ms and leaves the rest of a second for the key derivation; 256 KB is 1.4 s and over the budget. In `DocumentState` this is the `whole` flag: one chunk covering everything, so the window covers everything and every edit is an ordinary edit in one field.
- **The window is cut again around the cursor on three triggers, and the third is the one that matters.** Near either edge is the obvious pair, and between them they answer deleting backwards and deleting forwards. The third is a ceiling on how much text the field may hold at all: text put into the *middle* of the window moves neither edge nearer the cursor, so nothing else would ever ask the window to move, and the field would go on holding everything pasted into it and laying all of it out again on every keystroke. That is the whole of why an editor gets slower the more has been pasted into it, and a ceiling is the whole of the fix.
- **What the view does when the window reaches backwards: it gives up the sliver of the top row that is already off screen, and nothing else moves.** The list finds its place again by the key of its top row, so a window that covered that row would leave it with nothing to find. Scrolling up by exactly the part of that row which is above the screen, plus one pixel, makes the row *before* it the one being held — and the window may then start there, because it is starting exactly where the anchor now is. Nothing jumps afterwards: the window draws that row's text at the same width in the same style, so it is the same pixels. **What makes the nudge small is that the cursor is kept on screen**, and that is a separate thing the editor has to do — see the next decision.
- **The editor scrolls the cursor into view itself.** The field lays out inside a list item and the list is what scrolls, so neither of them knows where a cursor is. Deleting backwards is what shows it: the text below the cursor moves up and the cursor does not, so a long run of backspaces walks it off the top of the screen, and the nudge above is only small while the cursor is near the top of the screen as well as near the start of the window. The two are one mechanism.
- **A selection that reaches outside the window is held as a mark over the document, not by the field.** Select-all on a gigabyte is not a thing a text field can hold, so the field goes on holding its few kilobytes with all of them selected, the rows draw the rest of the mark themselves, and the next edit made while the mark stands replaces the whole of it in the document rather than the run a diff would name. Nothing is decoded, laid out or copied to do it, so select-all costs the same on a gigabyte as on a line. The mark is dropped the moment the field's own selection stops being the whole of it, which is what a tap or a cursor move does.
- **Undo walks back what the user did, and nothing the editor does on its own has a say in it.** Every change the user makes is stored as it happens, so no state the text passed through can be lost by any route. Cutting the window, catching the rows up, committing — anything internal — is not a change and does not shape one. What one press takes back is what is reasonably one change: a run of editing in one place with no pause of a second or more, or one discrete action such as a paste, a cut or a replace. Nothing is collapsed but changes that follow one another immediately, and a change that on its own changes nothing is dropped. There is one history: the keyboard's undo keys, which arrive as ordinary key events, and the toolbar's buttons both ask the document, and the text field keeps none of its own. A remembered change holds the text it deleted in undo's own buffer, never a pointer into the opened file, so saving does not end the history.
- **The rows are a frame behind the document while the window is open, and that is what makes recording every keystroke affordable.** Everything typed lands inside the window, so every row outside it is drawing exactly the text it was drawing before — only its offsets have moved. Telling them costs the whole of what a commit costs: re-indexing chunks, and a new key for every row after the cursor, which is a fresh layout of each of them. Per keystroke that is tens of milliseconds and no editor can pay it. So the document is written to as it happens and the rows go on addressing it as it stood when the window opened; the commit that moves them on is the one that was already happening whenever the window is cut, focused, walked back or saved. Everything that indexes chunks or names a row is in the rows' frame, everything inside `Content` is in the document's, and the window's own growth is the only difference between them — which is what `shifted` crosses, and what it has always crossed, since the window was always holding text the document had not been told about.
- **Typing that carries straight on from what was typed last is the same piece, not another one.** Without that, a splice costs a piece per commit and every later splice walks all of them, which is an editor that gets slower the longer it has been open. With it, five hundred separate insertions at an advancing cursor are two pieces.
- **The buffer holding what was typed is append-only, so something has to let go of what nothing names any more.** Paste a megabyte, delete it, paste another: both are still in there, and only a save collapses them. Compaction is the answer and it has one subtlety worth writing down — the pieces the *remembered changes* are standing on have to be counted as still named, or walking one of them back would find its bytes somewhere else. It runs only once the buffer is large enough to matter and then not again until it has doubled, so a buffer that is all still in use is not copied over and over to learn that.
- **Everything under the last row is a tap target, and it belongs to the list rather than to the blank space at the end.** Blank space at the end can only be as tall as it was made, so a document shorter than the screen — one just opened, and every new one — would leave the ground below it deaf, with the one empty line at the top as the only way in. The list is the thing that is always the size of the screen, so the tap goes on it: rows and the field each consume their own taps and a drag is consumed as a scroll, so what reaches the list is a tap that landed on nothing, which is exactly the case that wanted answering. Where it puts the cursor is the end of the document, which is what tapping past the end of the text means anywhere else.
- **The window asking for focus is a question addressed to one window, and it is answered by the field actually being focused rather than by anyone taking the question.** Cutting the window again leaves two rows alive for a moment: the one being replaced re-runs its effects before the new one composes, and both are asking. A bare flag is taken by whichever runs first, which is the row about to be disposed, and it goes out with it — the field that survives is never focused, Compose ends its input session, and the keyboard shuts with no way back. So the ask names the window it is for, and a row left over from the last position does not match it. That is not enough on its own either: the row that does match can be disposed, or have its effect cancelled by the next cut, while it waits a frame for the layout — so what clears the ask is the field reporting that it holds focus, and until that happens the ask still stands for whoever composes next.
- **The activity takes configuration changes itself rather than being rebuilt**, rotation and a switch into dark mode included. A rebuild drops the open document, and nothing could bring it back: the descriptor the document reads through and the pieces standing on it are not something a saved instance state can hold, and no persistable permission is held that would let the file be opened again. That holds until there is somewhere to persist to, and even then re-opening a file loses unsaved edits, so it is the wrong answer for an editor.
- **There is one open file, always, and unsaved edits are never thrown away without asking.** Whatever opens a file — New, Open, or another app handing one over — replaces the document on screen rather than adding another copy of Edit beside it, and anything that would drop unsaved edits asks first. That holds everywhere the app can see it coming. What it cannot see is out of reach: swiping Edit away from recents, or the system killing it in the background, gives the app no chance to ask.
- **While the keyboard is up the screen is the text's, and only something worth seeing mid-sentence takes a line of it back.** In landscape the keyboard leaves a few lines, and whatever stays on screen while typing comes out of them. The file row and the name bar go with the keyboard. The bar says which file is open or what just happened to it, and what it says decides whether it stays: a file just opened or just saved holds it over the keyboard for two seconds, and a warning — an open or a save that failed, a file rewritten under the document — holds it until two seconds after the user next presses the screen or changes the text. Waiting for the user rather than for a clock is what stops a warning coming and going while nobody was looking, and the two seconds after is what stops the touch that noticed it from taking it away. Opening and saving while they run hold nothing. The bar pushes the text down rather than covering it, so the cursor can never be under it.

## Environment

- **One UI publishes the phone's accent in the old palette resources and not in the new role ones, so Compose's dynamic colour misses it.** There are two sets: the `system_accent1_*` tonal ramp from API 31, and the colour roles API 34 added on top — `system_primary_dark`, `system_primary_light` and the rest. Compose reads the roles where they exist. One UI fills in only the ramp, leaving the roles at the AOSP default blue, so `dynamicDarkColorScheme` hands back a blue that has nothing to do with the phone. The accent is published and simply not looked at; reading the ramp and mapping the tones the way Material does gets it back. The neutrals are split the same way and nothing here is drawn in them, so they are left as they come. This was pinned down without a build by asking the framework what the app resolves each colour to, and the answer disagreeing with what the app draws is itself the finding.
- **The two decoders disagree about where the input buffer sits after a bad byte, and neither says so.** `CharsetDecoder`'s contract is that a malformed result leaves the input position pointing *at* the bytes it objected to, and a desktop JVM does that. Android's — ICU-backed — comes back already *past* them, while still reporting the run's length, so trusting either the position or the length skips a byte. The tell is a valid character disappearing from the screen right after a bad one: `C3 28` in UTF-8 shows as one replacement with the `(` gone. What works on both is to ignore the position entirely and work out where the good part ended from the characters it produced, since a strict decode is a bijection and the characters say exactly how many bytes they came from.
- **Android's decoder also reports a bad run that reaches past the first byte**, which matters more than it sounds: a file in some single-byte encoding is ordinary text with a bad byte every few words, and a run that swallows the byte after each one takes readable characters off the screen. Resuming one code unit past the error instead gives one replacement per byte that cannot be named and keeps every byte that can.
- **Lowering `WINDOW_MAX` to make the ceiling reachable does not give a smaller window, it gives an editor that cuts the window on every keystroke.** The window is whole chunks and never fewer than one, so it cannot be made smaller than about a chunk however low the ceiling is set. Put the ceiling under that and `tooLong` is true for ever: every change re-cuts, every re-cut disposes the row, and failures appear that no real ceiling can produce. The natural window is roughly three chunks, which is where the real ceiling already sits. Grow the document with real pastes instead and let the ceiling arrive on its own.
- **Samsung's Clipboard Manager panel closes itself whenever the field is disposed.** Re-cutting the window restarts Compose's input session, and the keyboard drops out of the panel back to the plain letters. A test that taps the same coordinate again then lands on whatever key is now there — a run of `3`s appeared in a document that was supposed to be receiving pastes — so the panel has to be re-opened before every paste, or at least checked for.
- **Asking for focus is not the same as raising the keyboard, and almost everywhere it looks like it is.** `requestFocus()` brings the IME up only where the field did not already hold focus. The window row is keyed on where it starts, so moving the window composes a new field, and a tap that moves the window therefore raises the keyboard — which is nearly every tap there is. The exception is a document of one empty line: the window never moves, so the field is the same field, and once the keyboard has been dismissed with Back the field still holds focus. A tap then puts the cursor back and leaves no keyboard under it, which reads exactly like the tap having been ignored. `LocalSoftwareKeyboardController.show()` alongside the focus request is what covers both, and it is a no-op whenever the keyboard is already up.
- **A focused text field keeps its `LazyColumn` item alive off screen, so scrolling away from the cursor disposes nothing and the keyboard stays up.** `BasicTextField` on a `TextFieldState` takes its focus through a `FocusableNode`, and that node pins the item it sits in for as long as it holds focus — read out of the foundation 1.12.0 jar, since nothing in the docs says so. The next keystroke then scrolls the list back to the cursor before anything can cut the window, so a cut never lands on a field that is off screen. It is the focus that keeps the row alive, not being the window: a window row without focus is disposed off screen like any other.
- **The toolbar's buttons divide the width by weight, so there is nothing to scroll.** The whole button takes the tap and not just its word, so the centre of one is a safe coordinate with a good half-button of slack in either direction. Read the bounds off `uiautomator dump` all the same, because they move with the font scale — and because **which row is on screen depends on the keyboard**: the file row is not there while the IME is up, and the file's name is there only while what it says is holding it. In landscape with the keyboard up the dump reported the name bar as 11 px tall while a screenshot showed it whole, so take its height from a screenshot.
- **The keyboard must be asked to resize and not left to the system, which picks per orientation.** With no `windowSoftInputMode` the activity is `adjustUnspecified`: portrait resized and landscape *panned*, and panning slides the whole window up to keep the cursor above the keyboard — which took the toolbar off the top of the screen and cut the file's name in half against the status bar. It looks like a layout bug and no amount of inset arithmetic can reach it, because the layout is correct and the window it is drawn in has moved. `adjustResize` in the manifest is the whole fix.
- **`safeDrawing` counts the IME, so padding a whole screen with it makes everything on that screen move when the keyboard opens.** Anything sized off what is left of the screen — a row whose height is a fraction of the shorter edge, say — then shrinks as the keyboard rises. The split that works is for the column to pay the top and the sides and for whatever sits against the keyboard to pay the bottom, IME included, on its own.
- **A file picked through the external storage provider is read and written through two different layers, and only the inode agrees between them.** Reads go through MediaStore and come straight off the disk; a read-write open goes through the storage layer every app shares. That descriptor reports another device (149 against 64820 here), and once written to, its own modification time: the time the copy loop ended, not the time the storage layer finished passing the bytes on to the file, which on 512 MB was 6 s later. Size agrees. So a stamp from a write descriptor never equals one from a read, and a save that compared the two whole took every file for replaced. A MediaStore link, as `am start` hands one over, is disk on both sides and hides this, and it is also much faster: the copy phase of a 512 MB save through the picker's link took 2 to 11 s against about 1 s. Replacing the file under a MediaStore link also takes the grant with it (next item), so testing replacement needs a file picked through Open.
- **A URI permission granted by an intent belongs to the file, not to the name.** Replace the file underneath and the grant is gone with it, and saving fails with `has no access to` even though nothing about the app changed.
- **A build is two JVMs with a 2 GB heap ceiling each.** The Gradle daemon runs `-Xmx2048m` and the Kotlin daemon another `-Xmx2048m`, and the Kotlin one lingers for two hours after it is done compiling (`--daemon-autoshutdownIdleSeconds=7200`). Kotlin daemons also pile up: `Detected multiple Kotlin daemon sessions` means more than one is alive, each with its own 2 GB ceiling. Worth clearing between sessions: `gradle --stop` handles the Gradle daemon, the Kotlin ones need `pkill -f 'KotlinCompileDaemo[n]'`. Write the pattern with a bracket like that, because a plain `pkill -f KotlinCompileDaemon` also matches the shell running it and kills the command itself — that shows up as exit code 144 out of nowhere.
- **`pkill -f 'KotlinCompileDaemo[n]'` still kills your own shell if the name appears anywhere else on the command line.** The bracket protects the pattern, not a second literal mention of it later in the same line — a `pgrep -af "KotlinCompileDaemon"` in the same command is enough to bring back exit code 144.
- **Lint has to be asked for, and costs 13 minutes.** `assembleDebug` does not run it and `lint { checkReleaseBuilds = false }` disables the release hook, so nothing in the normal flow ever checks. `gradle lintDebug` works — 13m 5s cold, no OOM, so it is safe to run unlike release — and writes `app/build/reports/lint-results-debug.{html,sarif}`. It prints nothing useful to the console; read the SARIF. Worth running occasionally rather than never, but not per change.
- **aapt2 is `pkg install aapt2`, a native aarch64 build, and `android.aapt2FromMavenOverride` in `~/.gradle/gradle.properties` is what points AGP at it.** AGP's own comes from Maven as a glibc x86_64 binary that cannot run under bionic, so without the override every build dies in `processDebugResources`. The setting is not in the repo because it is an absolute path for this machine only.
- **SDK is at `~/android-sdk`, installed by a real `sdkmanager`** (cmdline-tools 22.0). `local.properties` points at it, so no `ANDROID_HOME` is needed. The cmdline-tools scripts ship a `#!/usr/bin/env` shebang that termux cannot resolve; `termux-fix-shebang` on `cmdline-tools/latest/bin/*` fixes it once.
- `platforms;android-37.0` is installed properly, with `package.xml`. `compileSdk = 37` resolves to `android-37.0` specifically — `android-37.1`, the Android 17 minor release, does not satisfy it.
- **AGP auto-installs `build-tools;36.0.0` and `platform-tools`, and both are x86_64.** aapt2 comes from the override and D8, R8 and apksigner are JVM tools, so an AGP task that shelled out to a native build-tools binary would fail with an exec format error.
- **Installing is `adb install -r app/build/outputs/apk/<variant>/app-<variant>.apk`**, straight from the build dir, and launching is `adb shell am start -n com.lucasta.edit/.MainActivity` for release and `adb shell am start -n com.lucasta.edit.debug/com.lucasta.edit.MainActivity` for debug — the activity keeps its unsuffixed class name, so the `.MainActivity` shorthand does not work with the debug package. `com.lucasta.edit.debug` is the package name to force-stop between runs.

## Known limits of the current editor

A number belongs to a limit for good and is never given to another, so the gaps are limits that have been answered or moved elsewhere, and the numbering is not to be tidied up.

5. No persistable URI permission is taken, so a file cannot be reopened after the process dies. Harmless until there is a recent-files list to reopen from.
7. **A drag-selection cannot cross the window's edges.** About a hundred lines of reach. The gesture is Compose's and belongs to one field, where editing crosses the edges because the window moves and select-all crosses them because it is a mark over the document.

## How the text is laid out

- **There is no buffer.** The document is a sequence of pieces over two places — ranges of the open file, and ranges of an append-only buffer holding what has been typed — and an edit rewrites the sequence rather than any bytes. What is in memory measures the editing and not the file: a gigabyte open costs about nine megabytes of heap.
- **Chunks.** `Chunks.kt` indexes the document into chunk starts of about 2 KB, cutting on line breaks so a chunk boundary falls where a line break already is and wrapping inside a chunk is what wrapping the whole document would have produced. A line with no break in it is cut at a space, which is the only place a boundary is visible, and never in the middle of a character. The index is an `IntArray` of byte offsets — no boxing anywhere — built off the main thread for documents over `INDEX_OFF_THREAD` (256 KB) and inline below that, where the hop off the main thread and back costs more than the scan. After an edit only the chunks the change fell inside are indexed again (`respan`); the span is widened to whole chunks first, or re-indexing from where the typing happened to start would put a boundary in the middle of a line.
- **Reading a run of the document allocates a fresh array every time**, so indexing a file allocates it once over in 64 KB pieces — 128 MB of short-lived garbage for a 128 MB file — and every row drawn allocates its couple of kilobytes. It never shows up in the process size, which stays flat, but it is the obvious thing to hand a reusable buffer to if indexing is ever made incremental, since that turns one burst of garbage into a steady trickle.
- **The scan is over bytes, and both size targets are scaled by the size of a code unit**, so a chunk holds about as much text whatever the file is written in. Reading raw bytes out of a `ByteArray` is fast interpreted and hot enough to be compiled — a window is 64 KB, tens of thousands of iterations per call — so the trick the old character scan needed, copying into a String to reach `String.indexOf`, is not needed here.
- **Rows.** `DocumentEditor` is a `LazyColumn` of chunks, so only the chunks on screen are ever measured and scrolling recycles them. A row's text is decoded when it is drawn and thrown away when it scrolls off. Fling and jump-to-anywhere come from `LazyColumn` for free. **Which rows there are is worked out from the chunk index rather than held as a list of rows**: a list is one object per chunk built again on every edit, and a chunk is two kilobytes, so on a large document that was hundreds of thousands of objects and megabytes of garbage per commit for an answer that is two comparisons and an addition.
- **The window.** One slice of the document — the chunk the cursor is in plus `WINDOW_CHUNKS` either side, about 6 KB — is a real `BasicTextField` and takes all the input, so IME, selection handles, magnifier and autocorrect are Compose's and not ours. Every other row is read-only `BasicText` that turns into the window when tapped. It follows the cursor: come within `WINDOW_GUARD` characters of an edge, or put more than `WINDOW_MAX` into it, and what changed is committed and it is cut again around the cursor. It is consulted on every change to the field rather than on every move of the cursor, which is the only way deleting forwards or pasting could ever reach it.
- **What the window commits is the run the typing actually touched, not the whole window.** A window is a few thousand bytes of which almost none was typed, and committing all of it would fill the typed buffer with text nobody typed and leave the file's own bytes for that run behind, which is exactly what byte pieces exist to avoid.
- **Encrypted documents opt out of all of it.** `load(whole = true)` gives the document a single chunk, so the window is the whole file and the layout is exactly what it was before chunking existed. See the design decisions for why.
- **The list holds its place by the key of the row at the top of the screen, so the window may never start above that row** — a row the window covers stops being a row, and the list then falls back on row numbers, which mean somewhere else once the window has collapsed a few rows here and given a few back there, and the text jumps.
- **`WINDOW_CHUNKS` is the dial.** The window is the only text a keystroke lays out again, so raising it buys a longer drag-selection and costs typing latency, at roughly 4 µs per character of window.

## Speed of opening

Driven by `adb shell am start -a android.intent.action.VIEW -d content://media/external/file/<id> --grant-read-uri-permission -n com.lucasta.edit.debug/com.lucasta.edit.MainActivity`, timings from `adb logcat -s edit.perf` (the `timed`/`frameAfterNext`/`heap` helpers in `Document.kt`, temporary). MediaStore ids come from `adb shell content query --uri content://media/external/file --projection _id:_display_name`.

| file | index | total open | first frame | heap after | process PSS |
| --- | --- | --- | --- | --- | --- |
| 32 MB | 165 ms | 234 ms | 75 ms | 11 MB | 124 MB |
| 64 MB | 276 ms | 289 ms | 63 ms | 8 MB | 119 MB |
| 128 MB | 520 ms | 538 ms | 53 ms | 12 MB | 120 MB |
| 1 GB | 4767 ms | 4820 ms | 171 ms | 9 MB | 143 MB |

Do not read `setText` in the log as the cost of the index: it is a suspend call, so on documents over 256 KB it is the index plus however long the main thread took to get back to the continuation, which during app startup is most of it. A first launch after an install runs about twice as slow across the board, so take the second run.

**The index is the last whole-file pass, and making it incremental is the next thing worth doing.** Index the first stretch, show the rows there are, and continue behind the list: the row count a `LazyColumn` insists on is a count, not the final count, and rows appended at the end do not disturb where anyone is looking. That is what would take a gigabyte from five seconds of nothing-on-screen to about as fast as anything else. What it has to handle is an edit landing while the tail is still being indexed — the offsets after it move — which is why the batch wants a generation stamp and a restart rather than a merge.

## File size

State: two caps, both refused with our own message — `MAX_FILE_BYTES`, the whole of what an `Int` can address, for plain files, and 128 KB for encrypted ones (`MAX_ENCRYPTED_BYTES`, see the design decisions). The format is sniffed from the first bytes before the size is checked against that format's cap, so a 292 KB file opens as text and is refused as an encrypted file. The size comes from `fstat` on our own descriptor rather than from a provider column, so there is no second opinion to be wrong.

**Nothing in memory scales with the file any more.** The heap holds the chunk index, the pieces, whatever has been typed, and the one slice the window is showing. The index is the only one of those that grows with the file, at four bytes per two kilobytes — one part in five hundred, so 2 MB for a gigabyte.

What is left is:

1. **`Int` addressing**, which is the cap. Every offset in the document, the index and the pieces is an `Int`, so 2 GB is the ceiling and the cap is set at it. Going past it means `Long` offsets through all four pure files, and it buys files this app almost certainly should not be opening.
2. **Patience with the index**, which is what actually bites first — about 4.7 ms per MB, so a gigabyte is five seconds with nothing on screen. Incremental indexing is the answer and is not written yet.
3. **The temporary a save writes**, which costs the document's size in app storage while the save runs, plus the same again copied over the file.

**Nothing here depends on the heap the device hands out**, so none of it is per-device.

## Not started

- **Undo must not depend on where the window was cut.** A cut is the editor's own choice, made in the background, and today it splits what one press of undo takes back. Nothing the user did not choose may shape what undo does.
- **A paste, a cut or a replace is an undo step of its own.** Today runs are joined by position and time alone, so a paste where the user was just typing joins that run and one press takes both back.
- **The text field is to keep no history at all.** Today it keeps one between cuts, cleared only when the window is cut, and it is out of reach only because the undo keys are taken before the field sees them.
- **The keyboard must not see the window being cut.** Where the window sits and how much it may hold are memory and display concerns, and the keyboard has to work as if neither existed. Today a cut replaces the field, so the keyboard gets a new input session: its panels close, the clipboard one included, and the word being composed is committed mid-word. At the end of a document the size ceiling is the only thing that ever cuts, so plain writing hits this every ten thousand characters or so. It matters beyond the interruption: cuts that cost nothing could come far more often, and a smaller window is a cheaper keystroke.
- **Tapping a line after scrolling away from where you typed makes the text jump.** Type something, scroll down until the place you typed is off the top of the screen, then tap a line further down: the cursor lands on the right spot, but the tapped line jumps to about a third of the way down the screen instead of staying under the finger. The same tap without typing anything first moves nothing.
- **Incremental indexing.** See the end of "Speed of opening". The largest remaining win and the last whole-file pass.
- **Nothing asks before unsaved edits are thrown away.** New and Open replace the document on the spot, and Back closes Edit, all with no warning. The change list makes the question exact rather than a guess: a document with nothing to walk back since it was opened or saved has nothing to lose.
- **Opening a file from another app while Edit is already open starts a second copy of Edit instead of replacing the document.** The new file opens on top, the old one stays open underneath with its edits, and Back returns to it, so the same file can end up open twice. Read off the code and not yet seen on the phone.
- **While a save copies over the file, the document is reading that same file.** Rows scrolled into view during a large save draw it half rewritten, and keep that until the next edit. A copy that fails partway leaves the document pointing into a file that is neither version. The switch onto the new file afterwards also runs on a background thread while rows may be reading the pieces on the main one. Read off the code and not yet seen on the phone.
- **Save as as the way out when saving is refused.** A file the app was handed read-only fails with `could not save: <package> has no access to <uri>`, which is accurate and useless. It should offer Save as instead, which is the same branch the collision dialog already has. The same thing happens after a file is replaced under an open document, since the grant that came with the intent belonged to the file that was there.
- Editor UI: find and replace, a scrollbar or some sense of where in the file you are. Find is the next one worth doing and it is now cheap to place: it works on the document, it can put the answer under the window the way a tap does, and the mark that select-all uses is already the way to show a match that is off screen.
- Encryption: passphrase entry, KDF, envelope format, decrypt-on-open / encrypt-on-close. The split is in place, `EncryptedFile.kt` is where it goes, and the magics it sniffs are age's only provisionally.
- Device-to-device backup posture. `allowBackup="false"` stops cloud backup on every supported version, but from Android 12 it does not stop device-to-device transfer — that needs `android:dataExtractionRules` with a `<device-transfer>` exclude, which costs an XML file. The app persists nothing at all today, so there is nothing to leak; do this when it first stores something, such as recent files, SAF permission grants or settings.
- **Undo keeps its own buffer of what the changes deleted, and does not depend on the file.** Today a remembered change points at the bytes it took out wherever they lie, the opened file included, so a save, which overwrites that file, has to throw the whole history away. Undo needs only the text its changes removed, so that text is kept for it in a buffer of its own, and the history then survives a save. The opened file is for the document and for noticing that something else changed the file, which is decided from its identity, size and time rather than from its contents.
