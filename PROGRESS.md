# PROGRESS

Progress tracker for **Edit** — a bare text editor for Android that opens and closes encrypted files in a format any tool can read and sync.

## Where the project stands

A working bare editor: open a file, edit it, save it.

- **Everything is on its latest stable release, checked against the actual repos rather than assumed.** AGP 9.3.1 (9.4.0 exists only as alphas), Gradle 9.7.0, Kotlin 2.4.10 (2.4.20 is Beta/RC), activity-compose 1.13.0, coroutines 1.11.0. The only move available was the Compose BOM, 2026.06.01 to 2026.08.00. Do not read the tail of a `maven-metadata.xml` and call it the latest — the `<release>` and `<latest>` tags there point at prereleases too; AGP's both said `9.4.0-alpha08`. Filter for stable explicitly.
- Source is six files: `MainActivity.kt` (edge-to-edge setup, theming, toolbar and open/save wiring), `Editor.kt` (`DocumentState` and `DocumentEditor`: the chunked layout and the editable window), `Chunks.kt` (the chunk index, pure and Android-free), `Document.kt` (the vocabulary both paths share, plus `openDocument`/`saveDocument`, which dispatch on the first bytes), `TextFile.kt` (the plain path: encoding detection, strict read, write) and `EncryptedFile.kt` (stubs). The theme is four lines inline in `onCreate`, not its own file or package.
- Release was last built before the theme work, minified by R8 and signed, at 1.5 MB. No proguard rules of our own were needed — AndroidX and Compose ship their own consumer rules. Verified then by dumping the APK, by `apksigner verify` (v2 scheme), and by installing it over adb and confirming it launches with nothing in logcat. **It has not been buildable since — see the OOM note below.** So the release APK in `app/build/outputs/apk/release/` and the installed release both predate the theme work, the version bumps and `isShrinkResources`.
- **`isShrinkResources = true` is set on release but has never been exercised**, because release does not build. It pairs with the `isMinifyEnabled` that was already there, so R8 strips unused resources as well as unused code. Unverified: if release ever builds again, check the APK still has its launcher icon and that `values-night/themes.xml` survived, since resource shrinking is exactly the thing that would wrongly drop a resource only referenced from a manifest theme attribute.
- No tests and no test dependencies. No crypto code yet.

## Design decisions

- **Encryption format must be tool-agnostic.** A single self-contained file (age, or AES-GCM + Argon2id envelope) that any desktop tool can decrypt. Explicitly NOT Jetpack Security / `EncryptedFile` — it binds keys to the device keystore, making files unreadable off-device.
- **File access via SAF**, so no storage permissions and any sync tool (Syncthing, rclone, etc.) owns the files.
- **Encrypted files are a separate implementation, not a mode of the plain one.** Its own read, its own write and its own cap, so crypto never gets threaded through the path that plain text uses and neither can quietly change how the other handles bytes. `readEncryptedDocument` and `writeEncryptedDocument` exist today only to fail with `NotSupported`.
- **An encrypted file is also laid out the old way: whole, in one text field, never in chunks.** Nothing about a plaintext should be inferable from how it is drawn, and a layout that measures only the part being looked at is one more thing that would have to be reasoned about before that could be claimed. Keeping the encrypted path on whole-document layout means there is nothing to reason about, and it costs only a cap: `MAX_ENCRYPTED_BYTES` is 128 KB, measured on the phone at 697 ms to lay out and about 800 ms from tap to text — under a second, with what is left of that second belonging to the key derivation. 256 KB was measured too, at 1.4 s, which is over the budget. In `DocumentState` this is the `whole` flag: one chunk covering everything, so the window covers everything and every edit is an ordinary edit in one field.
- **The activity takes configuration changes itself rather than being rebuilt**, rotation and a switch into dark mode included. A rebuild drops the open document, and nothing could bring it back: the buffer is orders of magnitude too big for a saved instance state, and no persistable permission is held that would let the file be read again. That holds until there is somewhere to persist to, and even then re-reading a file loses unsaved edits, so it is the wrong answer for an editor.

## Environment

Everything below is plain `pkg install` or a stock SDK — no hand-assembled pieces, no version fictions, nothing that needs to be worked around.

- **`gradle assembleRelease` gets the low-memory killer to take out everything on the device**, including the terminal, even with Termux set to unrestricted power mode. So release is not a build we run to check our work — that is what the debug app is for. Only build release when there is an actual reason to ship one, expect to lose the session when you do, and do not casually run it for verification.
- **It is R8 specifically, and it is not memory accumulating over a session.** Tested from as cold a start as exists, with no java processes alive at all. It died anyway, at exactly the same point. The log ends on `reportReleaseComposeMappingErrors` and `minifyReleaseWithR8` never printed its task header, so R8 is where it goes. There is no `OutOfMemoryError` anywhere in the output, which is the tell that the JVM never failed — it was SIGKILLed from outside, so expect no error message and no stack trace, just a log that stops.
- **Kotlin daemons do pile up.** A build warned `Detected multiple Kotlin daemon sessions` and two `KotlinCompileDaemon` processes were alive at once, each with its own 2 GB ceiling and `--daemon-autoshutdownIdleSeconds=7200` keeping it around for two hours. Worth clearing between sessions: `gradle --stop` handles the Gradle daemon, the Kotlin ones need `pkill -f 'KotlinCompileDaemo[n]'`. Write the pattern with a bracket like that, because a plain `pkill -f KotlinCompileDaemon` also matches the shell running it and kills the command itself — that shows up as exit code 144 out of nowhere.
- **Opening a big file in the app is itself a memory event, and it can take the session down.** At the 32 MB cap the app is 257 MB of RSS; opening 32 and 64 MB files repeatedly while the Gradle and Kotlin daemons were alive got the low-memory killer to cull everything, terminal included. Same ending as an `assembleRelease`, from the other direction. Before testing anything above a few MB: `gradle --stop`, clear the Kotlin daemons, and do the build first and the opening afterwards. What survives a cull is everything on disk; what dies is the daemons and the adb server.
- **`pkill -f 'KotlinCompileDaemo[n]'` still kills your own shell if the name appears anywhere else on the command line.** The bracket protects the pattern, not a second literal mention of it later in the same line — a `pgrep -af "KotlinCompileDaemon"` in the same command is enough to bring back exit code 144.
- **A build is two JVMs with 2 GB heap ceilings each.** The Gradle daemon runs `-Xmx2048m` and the Kotlin daemon another `-Xmx2048m` (with `--daemon-autoshutdownIdleSeconds=7200`, so it lingers long after it is done compiling). That is 4 GB of ceiling on a device with far less than that free, and R8 is the task that actually tries to climb toward it. Untried ideas, in the order worth trying: kill the Kotlin daemon after `compileReleaseKotlin` so its heap is free when R8 runs, since a resumed `assembleRelease` will find the Kotlin output up to date and go straight to R8; run that second phase `--no-daemon` so only one JVM exists; and cap `org.gradle.jvmargs` so R8 fails cleanly with a Java OOM instead of taking the session down with it.
- **Lint has to be asked for, and costs 13 minutes.** `assembleDebug` does not run it and `lint { checkReleaseBuilds = false }` disables the release hook, so nothing in the normal flow ever checks. `gradle lintDebug` works — 13m 5s cold, no OOM, so it is safe to run unlike release — and writes `app/build/reports/lint-results-debug.{html,sarif}`. It prints nothing useful to the console; read the SARIF. Worth running occasionally rather than never, but not per change.
- Gradle 9.7.0 comes from `pkg install gradle` — the same version `gradle-wrapper.properties` pins. `gradlew` is still in the repo and correct for anyone else, but the wrapper distribution was never downloaded here, so `./gradlew` would pull 130 MB from `services.gradle.org` to arrive at the same Gradle. The termux mirror runs about 10x faster than Google's, which is why the packaged one won.
- JDK is `openjdk-21` (21.0.12). AGP compiles to JVM 17 bytecode regardless, per `compileOptions` and the `kotlin` block.
- **aapt2 is `pkg install aapt2`**, a native aarch64 build reporting `2.20-android-16.0.0_r4` — genuinely build-tools 36 era, which is what AGP 9 expects. `optimizeReleaseResources` runs and produces a correct APK, so the old `android.enableResourceOptimizations=false` workaround is gone.
- The one setting that has to stay is `android.aapt2FromMavenOverride`, pointing at `/data/data/com.termux/files/usr/bin/aapt2`. AGP's own aapt2 comes from Maven as a glibc x86_64 binary that cannot run under bionic, so without the override every build dies in `processDebugResources`. It lives in `~/.gradle/gradle.properties`, not in the repo, because it is an absolute path for this machine only.
- **SDK is at `~/android-sdk`, installed by a real `sdkmanager`** (cmdline-tools 22.0). `local.properties` points at it, so no `ANDROID_HOME` is needed. The cmdline-tools scripts ship a `#!/usr/bin/env` shebang that termux cannot resolve; `termux-fix-shebang` on `cmdline-tools/latest/bin/*` fixes it once.
- `platforms;android-37.0` is installed properly, with `package.xml`. `compileSdk = 37` resolves to `android-37.0` specifically — `android-37.1`, the Android 17 minor release, does not satisfy it.
- **AGP auto-installs `build-tools;36.0.0` and `platform-tools`, and both are x86_64.** Nothing executes them: aapt2 comes from the override and D8, R8 and apksigner are JVM tools. The debug build in fact succeeded before build-tools existed at all. Worth remembering only if some future AGP task shells out to a native build-tools binary, which would fail with an exec format error.
- **Nothing installs an APK from the termux shell except adb.** Four routes were tried and each is walled off differently. `pm install` fails because SELinux denies `system_server` access to `app_data_file`, so it cannot read the build dir; it suggests `/data/local/tmp`, which an app uid cannot write to. `content query`, which would get a MediaStore URI the way a file manager does, needs the privileged `ACCESS_CONTENT_PROVIDERS_EXTERNALLY`. `am start` is refused because it identifies as `com.android.shell` while running as our uid, so `assertPackageMatchesCallingUid` throws. `termux-open` does raise the install prompt — Termux has "install unknown apps" granted — but the installer rejects its FileProvider URI, with or without an explicit `--content-type`, and whether the APK sits in the build dir or in `~/storage/downloads`. The installer only accepts a `content://` URI, Termux's provider is the one it refuses, and every tool that could mint an acceptable URI needs a privileged permission.
- **adb is paired and this is now the way we install.** `pkg install android-tools`, a native aarch64 build. `adb install -r app/build/outputs/apk/release/app-release.apk` streams the APK over a socket rather than handing over a path or a URI, so none of the walls above apply and it works straight from the build dir with no copying and no tapping. `adb shell am start -n com.lucasta.edit/.MainActivity` launches it, and `adb logcat` finally gives us crash output.
- **Reconnecting after a reboot or a Wireless debugging toggle.** Pairing itself survives, but the connect port changes every time, so it needs `adb connect <ip>:<connect-port>` with the port read off the main Wireless debugging screen. That screen is not a popup, so it can be read after switching apps. This adb has no mDNS support, so `adb mdns services` errors out and the port cannot be discovered automatically. The adb server also dies on its own between commands here — when a command reports `daemon not running; starting now` and then `no devices/emulators found`, the fix is just `adb connect` again on the same port, which is still valid. Cheap enough to prefix onto any adb command after a gap. **After an OOM kill the server comes back wedged, and `adb connect` alone will not fix it** — it reports success or silence and `adb devices` still lists nothing. `adb kill-server` then `adb start-server` then `adb connect` recovers it on the same port. Do not conclude from a failed `adb connect` that the port changed; check with a server restart first, because reading a new port off the phone needs the user.
- **Pairing again, if it is ever needed, requires split screen.** Android invalidates the pairing session the instant the pairing dialog is dismissed, and switching apps dismisses it — so the code can never be relayed by switching to the terminal. What that failure looks like is `error: protocol fault (couldn't read status message)`, which reads like a broken adb and is not one; the termux issue for it is closed as not-bug. Put Settings and the terminal side by side in split screen, then run `adb pair <ip>:<pair-port> <code>` while the dialog is still on screen. The pairing port and the connect port are different.
- Falling back without adb means `cp` to `~/storage/downloads` and tapping the file by hand in a file manager.

## Known limits of the current editor

1. **Only files that survive a byte-exact round trip will open at all.** A file with a few corrupt bytes is refused outright, even though it might be worth reading. There is a TODO in `TextFile.kt` for offering to open it anyway as a deliberate choice, with a clear warning that saving will rewrite the bytes that could not be represented and that a backup must exist first.
2. Legacy single-byte encodings are rejected. Latin-1 and Windows-1252 accept any byte sequence, so they cannot be detected, only guessed at. A file of Latin-1 accented text will simply refuse to open.
3. No unsaved-changes tracking, so opening a second file, or starting a new one, silently throws away edits to the first.
4. The whole file is read into one String. See "File size".
5. No persistable URI permission is taken, so a file cannot be reopened after the process dies. Harmless until there is a recent-files list to reopen from.
6. **Save fails outright when the app was handed read-only access.** An `ACTION_VIEW` intent that grants read but not write gives `could not save: <package> has no access to <uri>`, which is accurate and useless — there is nothing the user can do with it. It should fall back to offering Save as, since that is the actual way out. Found while testing, by granting only read: `--grant-read-uri-permission` without `--grant-write-uri-permission`.
7. **A drag-selection cannot cross the window's edges.** Select-all, find and replace will not have this limit when they exist, because they work on the buffer and not on what is laid out, but dragging a selection handle stops at the window. About a hundred lines of reach.
8. **Scrolling away from the cursor closes the keyboard**, because the window row is a `LazyColumn` item and scrolling it off screen disposes it. The cursor and the edit survive; only the focus does not.
9. **Typing thousands of characters at the very end of a file grows the window** instead of moving it, since there is nothing after it to move into, and a growing window is a growing per-keystroke layout.
10. An edit shifts the offsets of every chunk after it, and the list is keyed on those offsets, so the scroll position can jump by a row or two when a window is committed while its neighbours are on screen.
11. **Tap in the topmost visible chunk and the window has no reach backwards**, because it may not start above the row the list is anchored on, so deleting or moving past the top of the screen does nothing until the view is scrolled up. The fix is to scroll first and then extend, and what makes it work is knowing where to put the view afterwards: that needs the pixel height of the chunk being put in front, which is not known until it has been laid out — so either heights are remembered as chunks scroll past, or the view goes somewhere defensible instead, like the window's own start at the top.

## How the text is laid out

This is what exists today, and the model decided further down replaces what sits underneath it: the buffer becomes a list of pieces and the chunk index counts bytes rather than characters. Everything about how the rows and the window behave survives that unchanged, which is why it is written down here rather than waiting.

The document is still one flat run of characters. What changed is that it is no longer handed to a text layout in one piece.

- **Storage is a `StringBuilder`, not a `String`.** Same shape — one contiguous run, no pieces, no index of the text itself, nothing to maintain — but writable in place, so flushing the window is one arraycopy of whatever follows it instead of allocating a fresh copy of the entire file. On a 16 MB document the String version allocated and discarded 32 MB every time the window moved. It lives exactly as long as the open file, and the only thing that ever turns it back into a String is nothing at all: `withText` hands the buffer itself to whatever is writing it out. Because it is written in place there is no new object for Compose to notice, so `version` is bumped on every change and everything drawn from the buffer is keyed on that.
- **Reading and writing both stream.** The file is decoded straight into the buffer as the bytes arrive, and written back out of the buffer as it is encoded, so nothing whole-file exists but the buffer itself. The old path held the file four times over — byte array, decoder's char buffer, String, then the copy into the buffer — and that, not the editor, was what capped the size we could open.
- **Chunks.** `Chunks.kt` indexes the document into chunk starts of about 2 KB, cutting on line breaks so a chunk boundary falls where a line break already is and wrapping inside a chunk is what wrapping the whole document would have produced. A line longer than 4 KB has no break to fall on and is cut at a space, which is the only place a boundary is visible. The index is an `IntArray` of offsets — no boxing anywhere — built off the main thread for documents over `INDEX_OFF_THREAD` (256 KB) and inline below that, where the hop off the main thread and back costs more than the scan. After an edit only the edited span is indexed again (`respan`), so committing costs the size of the window and not the size of the file. `chunkStarts` takes a `CharSequence` but never reads through it: it copies the document out 64 KB at a time into a String and scans that with `indexOf`. Reading characters through `CharSequence.get` measured 500 ms on a 16 MB file **and did not get faster on a second run in the same process**, which rules out warm-up and points at the loop never being compiled at all — it is entered a few thousand times and runs a couple of thousand iterations each time, under the threshold for both the method and the loop, while `String.indexOf` is an intrinsic that is fast interpreted. Copying 7% extra and letting the intrinsic look costs 245 ms instead of 500 ms.
- **Rows.** `DocumentEditor` is a `LazyColumn` of chunks, so only the chunks on screen are ever measured and scrolling recycles them. Fling and jump-to-anywhere come from `LazyColumn` for free.
- **The window.** One slice of the document — the chunk the cursor is in plus `WINDOW_CHUNKS` either side, about 6 KB — is a real `BasicTextField` and takes all the input, so IME, selection handles, magnifier and autocorrect are Compose's and not ours. Every other row is read-only `BasicText` that turns into the window when tapped. The window follows the cursor: come within `WINDOW_GUARD` characters of its edge and it is flushed back into the document and reopened around the cursor. So no action is confined to where it started — only a single drag-selection is, and only at the window's edges, which is about a hundred lines away rather than one line.
- **Encrypted documents opt out of all of it.** `load(whole = true)` gives the document a single chunk, so the window is the whole file and the layout is exactly what it was before chunking existed. See the design decisions for why.
- **The list holds its place by the key of the row at the top of the screen, so the window may never start above that row** — a row the window covers stops being a row, and the list then falls back on row numbers, which mean somewhere else once the window has collapsed a few rows here and given a few back there. That was the jump when tapping after a long scroll.
- **`WINDOW_CHUNKS` is the dial.** The window is the only text a keystroke lays out again, so raising it buys a longer drag-selection and costs typing latency, at roughly 4 µs per character of window. Nobody has measured typing latency yet.

## Speed of opening

Measured by driving `adb shell am start -a android.intent.action.VIEW -d content://media/external/file/<id> --grant-read-uri-permission -n com.lucasta.edit.debug/com.lucasta.edit.MainActivity`, timings from `adb logcat -s edit.perf` (the `timed`/`frameAfterNext`/`heap` helpers in `Document.kt`, temporary). MediaStore ids come from `adb shell content query --uri content://media/external/file --projection _id:_display_name`.

Before chunking, laying out the text was linear at roughly **5 seconds per MB** — 64 KB 252 ms, 512 KB 2.3 s, 1 MB 5.2 s, 4 MB an ANR with 1.1 GB resident — and a plain `EditText` behind `AndroidView` ANR'd at 4 MB too, so it was never about which widget. Now the first frame lays out only what is on screen and the cost is flat:

| file | read | chunk index | total open | first frame |
| --- | --- | --- | --- | --- |
| 4 MB | 147-319 ms | 106-171 ms | 442-530 ms | 62-81 ms |
| 16 MB | 402-587 ms | 237-239 ms | 764-933 ms | 65-85 ms |
| 32 MB | 527-566 ms | 415-420 ms | 999-1052 ms | 63-86 ms |
| 64 MB | 725-811 ms | 776-782 ms | 1581-1649 ms | 76-110 ms |

Two runs each, ranges rather than single numbers because a single number here is a lie: whatever else runs on the device during a measurement can triple a figure — the tell is that read and index move together. 64 MB is over the cap and is in the table because it is what the cap decision was made against. **The first frame is flat at 60-110 ms whatever the file size**, which is the whole point of the chunking; everything else in the row is whole-file work.

Read and index both scale with the file now — roughly 25 ms and 12 ms per MB — and between them they are the whole of an open. Reading got slower than when it held the file four times over, because filling the buffer is a real 32 MB of writing at 16 MB and there is no longer anything else doing that work first; that is the trade for the memory it no longer uses. A first launch after an install runs about twice as slow across the board, so take the second run. The idea that would make the index flat is to index lazily — index the first screens, extend as the list asks for more — but the `LazyColumn` needs to know how many rows there are, so that is not free.

Do not read `setText` in the log as the cost of the index: it is a suspend call, so on documents over 256 KB it is the index plus however long the main thread took to get back to the continuation, which during app startup is most of it.

Dropped along the way: the re-encode round-trip check, which was 262 ms of the 527 ms an open took at 4 MB and proved nothing the strict decode had not.

## File size

State: two caps, both refused with our own message — **32 MB** for plain files (`MAX_FILE_BYTES`), 128 KB for encrypted ones (`MAX_ENCRYPTED_BYTES`, see the design decisions). `inspect` sniffs the format from the first bytes first and only then checks the size against that format's cap, so a 292 KB file opens as text and is refused as an encrypted file. The size comes from the SAF size column before opening, and `Capped` holds the same limit against the bytes as they arrive, for a provider that reports no size or the wrong one.

**Nothing about the editor caps it any more.** Reading streams, writing streams, and layout only ever touches what is on screen. Three things cap it now, in the order they bite:

1. **The buffer is two bytes per character.** A Java char is 16 bits, so a 32 MB file is a 64 MB buffer, and a 256 MB heap (a common `dalvik.vm.heapgrowthlimit`) puts a hard ceiling near 96 MB no matter what else is done. The heap is what refuses first, and it refuses by crashing, which is why there has to be a cap at all rather than letting people find out.
2. **`StringBuilder` doubles when it runs out of room**, allocating the new array while the old one is still alive. At 32 MB that is 64 MB growing to 128 MB with 64 MB still held — tight but survivable. At 64 MB it is not survivable. The buffer is therefore sized on load to the file plus a megabyte of slack, so ordinary typing never triggers a growth at all.
3. **The device, not the app.** At the 32 MB cap the process measures 202 MB PSS and 257 MB RSS — `adb shell dumpsys meminfo com.lucasta.edit.debug`. That is what the low-memory killer reads, and on a device with little memory available and a Gradle daemon in the room it is enough to start a cull. See the environment note.

64 MB was measured opening in 1.6 s at 153 MB of heap, so **raising the cap is one constant plus a decision about (2) and (3), not more work**. It is set at 32 MB because that is the largest size where the app can still be typed into without the growth in (2) being fatal.

**The cap belongs to a device, not to Android.** 32 MB is the right number for a 256 MB heap, which is what the device it was chosen on hands out. That ceiling is per-device and the spread is wide, so a constant chosen on one device is wrong on other hardware in both directions. The cap wants to come from the heap the app is actually given, and that has to happen before it ever runs anywhere else — unless the model below lands first, in which case the whole question goes away.

## The document as the file plus its changes

Decided, not started. Everything about how large a file can be follows from holding it, so the way past the cap is to stop holding it: the document becomes the file where it lies plus a list of the changes made to it, and what is in memory measures the editing rather than the file. Undo is the same list read backwards, so it arrives with this and not separately.

**The document behaves as a whole copy of the file taken the instant it was opened.** What a save writes is that copy with our edits in it and not one byte from anywhere else — never something another tool put there in the meantime, whether it appended, rewrote or replaced. The change list is only how a copy that large is afforded; everything below is in service of the copy being exact, and the one case that is refused is refused because it is the only way the file could get in.

- **A change list, not text.** The document is a sequence of pieces, each one either a range of the file or a range of a buffer holding what has been typed, and an edit rewrites the sequence rather than any characters. What the window commits is the span it actually changed, not the whole window, or the typed buffer fills up with text nobody typed.
- **Coordinates are bytes.** A piece is a byte range whichever side it points at, so a range nobody edited is copied to the output exactly as it came in and only the parts that were touched are ever decoded or encoded. That makes a save incapable of corrupting what was not edited, and it makes a file that no decoder round-trips openable and editable, which is limit 1. The cost is that everything looking for a line break has to look in code units and not in bytes, since in UTF-16 a byte 0x0A is only sometimes a line break.
- **A file we cannot seek in is not opened, and this is settled.** Every provider backed by a real file on the phone gives a seekable descriptor, which is every file this app exists for; the ones that stream their content instead are refused with a message.
- **The open descriptor is the snapshot, so nothing is copied and opening stays as fast as it is.** A descriptor pins the file it was opened on, not the name: a tool that replaces the file — writing a temporary and renaming over it, which is what Syncthing and rclone do — leaves what we are reading alive and intact until we close it, whatever the name now points at. That is a real snapshot for the price of holding one descriptor. The bytes stay on disk rather than in memory, so it costs the space of the replaced file until the document is closed.
- **A tool that writes in place is the case a descriptor cannot cover, and it is `fstat` that catches it, not a hash.** Rewriting the same file rather than replacing it changes what we are reading under us, and size and mtime read back off our own descriptor say so for nothing — where a hash costs a full read of the file to learn the same thing, and could still only ever say that bytes are gone, never bring them back. So it is refused with a message and the document is not silently half old and half new.
- **A save onto a file that changed since it was opened asks first: overwrite, save as, or cancel.** This is the ordinary collision — sync brought a newer version while the document was open — and the document itself is fine, since the descriptor kept it; the only question is whose version the file ends up holding, and that is the user's to answer, not ours. Size and mtime recorded at open are what the question is asked from. The save-as branch is the same one limit 6 wants for a file we were only ever given read access to.
- **Saving is the one place a copy is unavoidable.** Writing through SAF truncates the file our own pieces still point into, so the output goes to a temporary in the app's storage and is copied over the file afterwards. That is two passes for a save and the file's size in space while it runs, and it buys back that a failed save leaves the original whole. It costs opening nothing, and it is not what limits how large a file can be.
- **What opening still costs is the index.** Chunk boundaries need a pass over the file, at roughly the read speed measured above, so a gigabyte is tens of seconds. Indexing the first stretch and continuing behind the list makes it start with the rows it has and grow — the row count a `LazyColumn` insists on is a count, not the final count, and rows appended at the end do not disturb where anyone is looking. That is the answer to the lazy-index idea filed under "Speed of opening".
- **The encrypted path keeps its own model** — decrypted whole, in memory, never a byte of plaintext on disk. No pieces into a file, and nothing written anywhere, temporaries included, that is not ciphertext.

## Verified on the phone

The read and write paths were both rewritten, so both were checked end to end rather than reasoned about. Status text read with `adb shell uiautomator dump /sdcard/ui.xml` — Compose publishes its text to the accessibility tree, which is far cheaper than screenshots and gives the exact string.

- UTF-8 with multibyte content and UTF-16LE with a BOM both open and render correctly, the BOM stripped.
- A file with a bad byte is refused with `not valid text`. The strict decode survived the rewrite.
- Both caps refuse with the right message and the right limit: 64 MB and 128 MB plain over 32 MB, a 292 KB age-magic file over 128 KB. A 60 KB age-magic file gets past the size check to `encrypted files cannot be opened yet`, which is the sniff working.
- 32 MB — the cap — opens in 1.1 s.
- Scrolling a long way and tapping a line leaves the line where it was tapped, in both directions.
- **The keyboard closes and reopens whenever the window moves**, since the window row is keyed on where it starts and moving it builds a new field with a new input session. Judged smooth enough to leave alone.
- **Save round trips are byte-identical**: UTF-8, UTF-16LE with its BOM, and a 16 MB file, all `cmp`-clean against a copy taken before saving, with the process staying at 189 MB PSS through the 16 MB write, which is the streaming write not copying anything.
