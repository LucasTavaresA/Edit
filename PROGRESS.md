# PROGRESS

Progress tracker for **Edit** — a bare text editor for Android that opens and closes encrypted files in a format any tool can read and sync.

## Where the project stands

A working bare editor: open a file, edit it, save it, undo it, at any size up to the cap. Everything where a mistake can corrupt a file quietly is pure Kotlin, kept free of anything Android, and the build has no test dependencies.

## Design decisions

- **The document reads only a private copy of the file, taken as it opens, plus its changes.** A save writes that copy with our edits in it and never a byte another tool put in the file meanwhile, and nothing writing to the file — appending, rewriting it in place, replacing it — can change the document under us. Reading the file in place would make opening copy-free, but an in-place rewrite would then change the document itself, which a hash can only report and never undo. It costs a pass over the file on every open and the file's size in app storage while it is open.
- **A file that does not decode is opened anyway.** Bytes nobody touched are saved exactly as they came in, so a byte the decoder cannot name is shown as a replacement and survives. What refuses a file is a zero code unit near its start, a rule about the file rather than about the decoder.
- **Crossing between characters and bytes is counted, not looked up, and has to agree with the platform on every input.** The byte arithmetic must match the encoder and the chunk index's character counts must match the decoder, malformed input and unpaired surrogates included, or offsets drift apart silently.
- **A file we cannot seek in is not opened, and this is settled.** Every provider backed by a real file on the phone gives a seekable descriptor, and a save is the file as opened plus tracked edits, so a streamed one cannot be supported.
- **Whether the file changed is decided by its contents, by hash, and by nothing else.** A new time on the file, or a sync tool putting identical contents back, is not a change; any write that leaves different bytes is. A save onto a file that changed since it was opened or last saved asks: overwrite, save as, or cancel, since whose version wins is the user's call. What is checked is the file actually being written over, before the write and by reading it back after, and the base moves only once the file is confirmed to hold what was written. Nothing on a phone makes another app wait, so a write landing during a save cannot be prevented, only never claimed as saved.
- **Opening, saving and New take turns across the whole process and every file, in the order asked.** Two saves at once would each find the other's write and report it as somebody else's, so opening a very large file makes a save in another file wait. Nothing is refused and no button goes off while one runs; a save writes the document as it stands when its turn comes, so presses while one waits join it, and a save that has started is never cut short, since a half copy leaves the file neither version.
- **Encryption format must be tool-agnostic.** A single self-contained file (age, or AES-GCM + Argon2id envelope) that any desktop tool can decrypt. Explicitly NOT Jetpack Security / `EncryptedFile` — it binds keys to the device keystore, making files unreadable off-device.
- **File access via SAF**, so no storage permissions and any sync tool (Syncthing, rclone, etc.) owns the files.
- **Encrypted files are a separate implementation, not a mode of the plain one.** Their own read, write and cap, so crypto never threads through the plain path and neither can quietly change how the other handles bytes. The file is decrypted whole, in memory, and nothing is written anywhere, temporaries and what was typed included, that is not ciphertext. It is laid out whole in one text field, never in chunks, so nothing about a plaintext can be inferred from how it is drawn; the cap keeps that layout to a fraction of a second beside the key derivation.
- **The window is cut again around the cursor near either edge and when it holds too much, and the ceiling is the one that matters.** Text put into the middle of the window moves neither edge nearer the cursor, so without it the window would keep everything pasted into it and lay all of it out again on every keystroke.
- **The list holds its place by the row at the top of the screen, so the window may never cover that row**, or the text jumps. When it has to reach back over it, the view gives up the off-screen sliver of that row first, which stays a small nudge only because the cursor is kept on screen.
- **The editor scrolls the cursor into view itself**, since the window is a list item and neither knows where a cursor is. It also brings the cursor back when the screen shrinks under it — the keyboard coming up, a turn to landscape — but leaves one the user scrolled away from alone.
- **A selection is two offsets into the document, never a text field's, so it reaches anywhere and costs the same on a gigabyte as on a line.** A touch and the keyboard make the same one, and there is only ever one. **The keyboard is told the mark itself, and what it does to the selection is done to the mark**: a keyboard builds each step of a gesture on the selection it last set, so answering with anything else breaks every keyboard, not one keyboard's quirk. The mark is told earlier end first, as a text field tells it, since keyboards count what a gesture deletes as end less start. The handles and their drag are the editor's, drawn over the rows; the magnifier and the menu are the platform's, pointed at them. A selection the keyboard makes or moves shows only its highlight, so a swipe never brings a menu up over the text. **A copy or a cut larger than the clipboard takes is refused, never cut short**, since a partial clip looks complete until it is pasted; a quarter of a megabyte is what it takes reliably, as each app has about a megabyte for everything crossing into the system at once and some of the system counts two bytes a character.
- **Undo walks back what the user did, and nothing the editor does on its own shapes it.** Cutting the window, catching the rows up and committing are not changes. One press takes back a run of editing in one place with no pause of a second or more, or one discrete action such as a paste. The keyboard's undo keys and the toolbar's buttons share the one history. **A change is remembered where it was made**, and undo puts the cursor back there: text put in or taken out next to a repeat of itself reads back the same wherever along the repeat it went, so the text alone cannot say where.
- **The rows are a frame behind the document while the window is open**, which is what makes recording every keystroke affordable: telling every row after the cursor that its offsets moved is tens of milliseconds a keystroke. The rows catch up at the commits that happen anyway. Anything that reads the document in the rows' terms has to allow for it, above all the list, and a commit while the screen is past the window holds the list's place by hand.
- **The history is a line of changes, and the document's place and the base, where the file was last in step, are two places on it.** Unsaved means the two differ, so undoing back to what was saved is saved. A place names a change rather than counting them, since after an undo new typing would bring a count back to a number it had before at a state never seen. The history points into the private copy and what was typed, never into the file, so it spans saves and nothing done to the file reaches it; that costs what was typed no longer being let go at a save. Compacting what was typed counts what the history stands on as still in use.
- **What a plain document typed moves onto disk once there is enough of it, and an encrypted one's never does. A disk that refuses it leaves it in memory**: a full disk costs heap and never an edit.
- **Everything under the last row is a tap target for the end of the document**, and it belongs to the list, which is always the size of the screen, so a document shorter than the screen still has somewhere to tap.
- **The keyboard is connected to the document, not to a text field, and the window is invisible to it.** The editor as a whole holds focus and the keyboard's session, so cutting the window starts nothing over: its panels stay open and the word it is working on stays its word. Everything it is told is in characters counted from the document's start, and true rather than merely consistent, since keyboards built on Android's own check the place they are given against the text before the cursor. Whatever a text field did for free is the editor's to do.
- **The activity takes configuration changes itself rather than being rebuilt**, rotation and dark mode included. The list of files is the process's and outlives a rebuild, but everything the screen holds does not: the keyboard's session and its word, the selection's handles and menu.
- **One Edit holds a list of open files, and only the first is on screen.** It is a single instance, so another app handing a file over reaches the running one and joins the list. Each file has its own document, link, name, messages, waiting save and question; Open and New add one on top, and a file already open is gone to rather than opened twice. The list is a stack: going to a file pulls it to the top and the rest keep their order.
- **Nothing in Edit throws unsaved edits away, so nothing asks.** Files are never closed: the list marks the unsaved ones and has no close button, a file once opened stays opened, private copy included, until Edit stops, and Back only sends Edit to the background. The one exception is a new file nobody has touched, with nothing even to undo: it leaves the list as soon as another file takes its place on top, so pressing New and moving on never piles them up. Swiping Edit away or the system killing it loses every file's unsaved edits, and that is expected rather than out of reach: what comes back is the list, never what was in it.
- **A start brings back the list, in order, and opens only the file that had focus**, or the one another app handed over; the rest stay unopened, with nothing copied or read, until the user goes to them, and are opened as they stand by then. What is kept is each file's link, name and access, never its contents, so unsaved edits and cursors do not come back. Access is kept for every file in the list and let go for every file not in it; a new file has nothing to come back as, and a file whose access ends with the process is not kept. The name is kept because a provider takes the access back once its file is deleted: going to such a file says it is gone and takes it out of the list, which is the only way anything leaves it. A file that fails to open for any other reason stays, and the screen stays where it was. A rebuilt activity is handed the intent that first started it, which says nothing about what is open by then, so it is not acted on again.
- **A message about a file behind the one on screen appears on the bar over whichever file is on screen**, so each one names the file it means, and the question about a changed file above all, since its answer overwrites that file. Such a message takes the bar briefly at least and then gives it back to the file on screen's own; a file gone to shows the last thing said about it.
- **While the keyboard is up the screen is the text's.** The file row and the name bar go with the keyboard. A file just opened or saved holds the bar over the keyboard briefly, and a warning holds it until a moment after the user next touches the screen or changes the text: waiting for the user rather than a clock stops a warning passing unseen, and the moment after stops the touch that noticed it from taking it away. The bar pushes the text down rather than covering it, so the cursor can never be under it.
- **Where the list stands is the document's, not the screen's, and nothing drawn for one document outlives it on screen.** The editor stays and keeps focus; handing it another document is all going to a file takes. **Going to a document puts the keyboard away and places no cursor**, whatever the document was left with, since a keyboard left up over a document with no cursor drops what is typed. Compose shows the keyboard whenever an input session starts, so a switch ends the keyboard's session and the next one starts only when the user puts the cursor somewhere. Compose also reports focus again whenever the editor is handed another document, so starting a session and the rule that gives arriving focus a cursor at the top row run only for focus that actually arrives. Rows are keyed on where they start and every document has a row at 0, so whatever is drawn or remembered for the rows and the touches is thrown away with the document rather than carried over to the next.
- **A pinch sizes the text: one size for every file, kept from one start to the next.** The text is laid out again at each step rather than scaled as a picture. **What stays under the fingers is the text, not a distance down the screen**, since lines wrap again at another size and a proportion lands lines away.
- **A long press on a link or an email address still selects the word, and the menu offers to open or select the whole of it**, never buttons on the bottom row. What counts is whatever Android's Linkify takes for a web or email address, the platform's answer rather than a pattern of ours; phone numbers are left out on purpose. Compose's text menu holds only its fixed items, so the menu is the platform's floating one.

## How the text is laid out

- **There is no buffer.** The document is a sequence of pieces over the private copy and what was typed, and an edit rewrites the sequence rather than any bytes.
- **Chunks are cut on line breaks**, so wrapping inside one is what wrapping the whole document would give; a line with no break is cut at a space. Only the chunks on screen are measured, and the rows are worked out from the index rather than held as a list.
- **The window is one slice around the cursor held as text, and everything typed lands in it.** **It commits only the run the typing touched**, never the whole window, or what was typed would fill with text nobody typed and leave the file's own bytes behind. Its size is a dial: typing latency against how often it is cut.

## File size

Two caps, both refused with our own message: 2 GB for plain files and a small one for encrypted ones. The format is sniffed before the size is checked against its cap, and the size comes from our own descriptor rather than a provider column.

**Nothing in memory scales with the file** but the chunk index, at about one part in five hundred. What limits size is:

1. **`Int` addressing**, which is the cap. Past 2 GB means `Long` offsets through all the pure files, for files this app almost certainly should not be opening.
2. **Patience with opening**, which bites first: two whole-file passes, the private copy and the index, so a gigabyte is many seconds with nothing on screen.
3. **App storage.** The copy costs the file's size while it is open, plus whatever typed text has moved onto disk. A save is three passes over the file — hash, write, read back — or the hash alone with nothing changed.

## Not started

- **Focus from a hardware keyboard's arrows puts the cursor at the start of the top row, which can be far above the screen.** A row is a whole chunk, so the cursor and the screen jump there. Rare, and left as it is.
- **Back, button and gesture alike, works like vim's jumplist**, stepping backwards through earlier cursor positions and across files. Until then it only sends Edit to the background.
- **Find out what happens when memory runs out** with several big files opened.
- **How long an unlocked encrypted file stays decrypted.** With multiple files it lives as long as a plain one, until Edit stops, so it sits readable in the background; better if it did not, but locking it on every switch is tiresome and gives files a second lifetime to manage. To be thought through later.
- **A paste, a cut or a replace is an undo step of its own.** Today runs are joined by position and time alone, so a paste where the user was just typing joins that run and one press takes both back.
- **What a text field gives that the editor does not yet.** Accessibility services see no editable field, so TalkBack can neither read the text as one nor edit it; a stylus cannot write into it; and a keyboard asking where the cursor is drawn on screen, for a floating preview or its own handwriting, is told nothing. None of them is anything a keyboard needs to type, select or edit.
- **The word a keyboard is composing has never been seen working.** Neither keyboard on the phone composes as it is set up, so the underline, a keyboard replacing the word it is working on, and that word staying whole across a window cut are written but unproven (CLAUDE.md says what proving them needs).
- **Incremental indexing.** The largest remaining win, for the patience with opening under File size; on its own it halves the wait rather than ending it, and to take the rest it would have to follow the copy as it is made. The list's row count is then not final, and an edit can land while the tail is still being indexed, moving every offset after it.
- **Save as as the way out when saving is refused.** A file handed over read-only, or replaced under an open document so the grant went with the old one, fails with `has no access to`, which is accurate and useless; it should offer Save as, as the collision dialog does.
- Editor UI: find and replace, a scrollbar or some sense of where in the file you are. Find is the next one worth doing.
- Encryption: passphrase entry, KDF, envelope format, decrypt-on-open / encrypt-on-close. The split is in place, and the magics sniffed are age's only provisionally.
- **An encrypted document's cap is checked as it opens and never again.** Editing can grow its text, and what the history keeps, past the cap, and a save would then write a file that opening refuses as too big.
- **A scroll cancelled while the editor follows the cursor ends the following for good.** The list refuses a scroll while a finger drag holds it, so text arriving mid-drag — a second finger, a hardware keyboard, voice typing finishing — would silently stop keystrokes being recorded as typed and the window following. Read off the code and not yet seen on the phone.
- **The process dying in the middle of a write leaves the file half-written.** Killed for memory once in the background, swiped away, a flat battery: writing over a file through the provider cannot be made atomic. The usual guard is a foreground service for the length of a save, which makes a kill far less likely.
- **A large paste holds the screen for as long as laying it out takes.** The window lays all of it out before it is cut back to size, so at a megabyte the system offers to close Edit. The window's ceiling answers every keystroke after the paste, and nothing answers the paste itself.
- **A clip that is a link to a text file is read whole as it is pasted.** The system turns such a clip into text by reading everything the link points at, in one go and on the main thread, before the editor sees any of it, so a link to a large file freezes Edit or runs it out of memory. Nothing in the clipboard's own limits catches it, since the clip itself is only a link.
- **Compacting what was typed runs on the main thread and costs what it keeps.** While it is all in memory that stays small; once it is on disk and holds hundreds of MB, it is a pause of seconds.
