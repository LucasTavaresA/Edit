# PROGRESS

Progress tracker for **Edit** — a bare text editor for Android that opens and closes encrypted files in a format any tool can read and sync.

## Where the project stands

A working bare editor: open a file, edit it, save it, undo it. The document is a private copy of the file plus a list of the changes made to it, the window you are typing follows the cursor wherever it goes, how much can be edited in one place is not a question at all. There is only one undo history that answers for everything, and saving does not end it.

- Everything where a mistake can corrupt a file quietly is pure Kotlin with no Android in it. The theme is a handful of lines, not a file or package of its own.
- No tests and no test dependencies. No crypto code yet.

## Design decisions

- **The document is a copy of the file taken as it opens, plus its changes.** What a save writes is that copy with our edits in it and not one byte from anywhere else — never something another tool put there in the meantime, whether it appended, rewrote or replaced.
- **Crossing between characters and bytes is arithmetic, not a table.** A strict decode is a bijection, so what a run of characters weighs in bytes is counted rather than encoded, and the only map kept is of where decoding was *not* a bijection — one entry per byte the encoding could not name, so ordinary text carries none, whatever it is written in. That is safe only while the arithmetic agrees with the encoder on *every* input and not only on well-formed input, unpaired surrogates included.
- **A file that does not decode is opened anyway.** A save copies every byte nobody touched exactly as it came in, so a byte the decoder cannot name is shown as a replacement and survives, and a file with a few bad bytes in it, or one in a single-byte encoding nobody can detect, is safe to read and to edit elsewhere in it. What refuses a file is a zero code unit near its start: text does not contain one and everything that is not text is full of them, and it is a rule about the file rather than about the decoder.
- **A file we cannot seek in is not opened, and this is settled.** Every provider backed by a real file on the phone gives a seekable descriptor, which is every file this app exists for; the ones that stream their content instead are refused with a message, since a save writes the file as it was when opened plus the tracked edits.
- **The copy is private, made as the file opens, and it is the only thing the document reads.** It lives in the app's own storage, unlinked, so nothing but the document can reach it, and no tool writing the file — appending, rewriting it in place or replacing it — can change the document under us. That is what makes every change to the file one question with safe answers. Reading the file in place instead would keep opening copy-free, but an in-place rewrite would then change the document itself, which a hash can only report and never undo. It costs a pass over the file on every open, on top of the index, and the file's size in app storage while it is open.
- **Whether the file changed is decided by its contents, by hash, and by nothing else.** The copy is hashed as it is made, and a save hashes the file before writing over it and after. The same hash is the same bytes, so a new time on the file, or a sync tool putting identical contents back, is not a change, and any write that leaves different bytes is, however it was made. Nothing stops a tool writing into the file while a save is copying into it, since nothing on a phone makes another app wait, and no lock is one other apps would honour: both writes land. What a save can do is not claim it — see the decision on saving below. A write the copy then covers entirely is gone, and nothing can see it.
- **A save onto a file that changed since it was opened or last saved asks first: overwrite, save as, or cancel.** Sync brought a newer version, or another app wrote into it; either way the document itself is fine, since it reads its own copy, and the only question is whose version the file ends up holding, which is the user's to answer, not ours. It is the only question there is: no change to the file leaves the document unable to be saved.
- **A save takes the document, writes what it took, and moves the base, and only the taking and the moving touch the live document.** The take is one step that nothing waits on, so typing is held up for well under a frame. What it took cannot be changed by anything the document does afterwards, so the write runs from it alone, off the main thread, straight into the file with no second copy, while the document goes on being edited. **What decides a save is the file actually being written over, not whatever its name leads to by then.** It has to hash the same as the base before the write, or the save asks and writes nothing; after the write it is read back, and anything that replaced it or wrote into it meanwhile makes the save ask the same question rather than say it saved. A save with nothing changed since the file was last in step writes nothing. **The base moves only once the file is confirmed to hold what was written**, so the document still counts as unsaved while a question is open. What a save reads stays alive until both the document and the save have let go of it, since the screen can close in the middle of one.
- **Opening, saving and New take turns, and however fast Save is pressed the file ends up holding everything up to the last press.** Two saves at once would write the same file at once, and each would find the other's write there and ask about it as somebody else's. A save ends by moving the base the next save's take reads and by naming the file it wrote, which an open or New in between would have replaced. So they run one at a time, in the order they were asked for, and the check before a save is part of the same operation as the write. The turns are the process's and not one screen's, so a second copy of Edit takes turns with the first — but nothing is refused and no button goes off while one runs: whatever is asked for meanwhile waits its turn. A save writes the document, and to the file, as they stand when its turn comes rather than when Save was pressed, so a press while a save is already waiting joins it, and a save that finds nothing changed since the file last held the document writes nothing. A save that has started is never cut short, since stopping one partway through the copy leaves the file neither version.
- **The encrypted path keeps its own model** — decrypted whole, in memory, never a byte of plaintext on disk. Nothing in the document points into a file, what was typed never moves onto disk, and nothing is written anywhere, temporaries included, that is not ciphertext.
- **Encryption format must be tool-agnostic.** A single self-contained file (age, or AES-GCM + Argon2id envelope) that any desktop tool can decrypt. Explicitly NOT Jetpack Security / `EncryptedFile` — it binds keys to the device keystore, making files unreadable off-device.
- **File access via SAF**, so no storage permissions and any sync tool (Syncthing, rclone, etc.) owns the files.
- **Encrypted files are a separate implementation, not a mode of the plain one.** Its own read, its own write and its own cap, so crypto never gets threaded through the path that plain text uses and neither can quietly change how the other handles bytes.
- **An encrypted file is laid out whole, in one text field, never in chunks.** Nothing about a plaintext should be inferable from how it is drawn, and a layout that measures only the part being looked at is one more thing that would have to be reasoned about before that could be claimed. Whole-document layout leaves nothing to reason about and costs only a cap: small enough that laying the file out leaves the rest of a second for the key derivation.
- **The window is cut again around the cursor on three triggers, and the third is the one that matters.** Near either edge is the obvious pair, and between them they answer deleting backwards and deleting forwards. The third is a ceiling on how much text the field may hold at all: text put into the *middle* of the window moves neither edge nearer the cursor, so nothing else would ever ask the window to move, and the field would go on holding everything pasted into it and laying all of it out again on every keystroke. That is the whole of why an editor gets slower the more has been pasted into it, and a ceiling is the whole of the fix.
- **The list holds its place by the row at the top of the screen, so the window may never cover that row.** A covered row stops being a row and the list loses its place, and the text jumps. When the window has to reach back over it, the view gives up the sliver of that row already off screen, so the row before it is the one being held, and nothing visible moves. That stays a small nudge only because the cursor is kept on screen.
- **The editor scrolls the cursor into view itself.** The field lays out inside a list item and the list is what scrolls, so neither of them knows where a cursor is. Deleting backwards is what shows it: the text below the cursor moves up and the cursor does not, so a long run of backspaces walks it off the top of the screen.
- **A selection is a mark over the document, never the field's, and it reaches anywhere, whatever makes it.** Select-all on a gigabyte, or a drag from the first line to the last, is not a thing a text field can hold, so a selection is two offsets into the document, the rows draw it, and an edit made while it stands replaces the whole of it in the document. Nothing is decoded, laid out or copied to hold one, so a selection costs the same on a gigabyte as on a line, and dragging one across the whole file fills nothing. A touch makes one and so does the keyboard — shift and the arrows, select all, a keyboard's own gestures, the swipe from backspace among them — and there is only ever the one. **The field holds exactly the part of the mark the window covers, as its own selection, and what the keyboard does to that is done to the mark**: an end it moves moves the mark's, an end the window cut short stays where it is, and collapsing it to a cursor lets go. A keyboard builds each step of a gesture on the selection it last set and reads it back to act on, so a field answering with anything else leaves it extending and deleting a selection that is not there; that is the contract every keyboard is written against, not one keyboard's quirk. It is also why a keyboard gesture started over a selection carries that one on rather than starting another. An edit over a mark the field holds whole is an ordinary edit of the field's, which leaves the keyboard's session and its panels alone; one over a mark reaching past the window replaces it in the document. The field never shows a selection as its own. The platform's handles, magnifier and menu belong to a field and reach no further than one, inside the window too, so every touch reaches the editor before any row does, the handles and the drag that carries them are drawn and driven over the rows, and the magnifier and the menu are the platform's own, pointed at them. They come with a touch and go once the keyboard moves the selection: one the keyboard makes or moves shows only its highlight, as a text field's own does, so a swipe never brings a menu up over the text. Copy, cut and paste are the editor's whichever way they are asked for, keys included. The one place size still counts is the clipboard: a copy or a cut larger than it takes is refused with a message and never cut short, since a clipboard holding part of what was asked for looks exactly like one holding all of it until it is pasted. What it takes reliably is a quarter of a megabyte of the document: text crosses into the system and back out in one go, each app has about a megabyte for everything crossing at once, and some of the system counts two bytes a character.
- **Undo walks back what the user did, and nothing the editor does on its own has a say in it.** Every change the user makes is stored as it happens, so no state the text passed through can be lost by any route. Cutting the window, catching the rows up, committing — anything internal — is not a change and does not shape one. What one press takes back is what is reasonably one change: a run of editing in one place with no pause of a second or more, or one discrete action such as a paste, a cut or a replace. Nothing is collapsed but changes that follow one another immediately, and a change that on its own changes nothing is dropped. There is one history: the keyboard's undo keys and the toolbar's buttons both ask the document, and the text field keeps none of its own. A remembered change points into the private copy and what was typed, never into the file, so saving does not end the history.
- **The rows are a frame behind the document while the window is open, and that is what makes recording every keystroke affordable.** Everything typed lands inside the window, so every row outside it is drawing exactly the text it was drawing before and only its offsets have moved. Telling them means re-indexing and laying out again every row after the cursor, tens of milliseconds a keystroke, which no editor can pay. So the document is written to as it happens and the rows catch up at the commits that were happening anyway, whenever the window is cut, focused, walked back or saved; the window's own growth is the only difference between the two.
- **Typing that carries straight on from what was typed last is the same piece, not another one.** Without that, every commit adds a piece and every later splice walks all of them, which is an editor that gets slower the longer it has been open.
- **What was typed is kept append-only, so something has to let go of what nothing names any more.** Paste a megabyte, delete it, paste another: both are still in there. Compaction lets go of them, and the pieces the *remembered changes* stand on count as still named, or walking one of them back would find its bytes somewhere else. It runs only once there is enough to matter and not again until that has doubled, so a buffer that is all still in use is not copied over and over to learn that, and it leaves the old buffer as it was for a save still reading it.
- **The history is a line of changes, the document stands at one place on it, and the base is another place on the same line: where the file was last in step, opened or saved.** Undo and redo move the document's place and a save moves the base, and neither touches the other. Unsaved edits means exactly that the two places differ, so undoing back to what was saved is saved, and what was typed during a save is unsaved after it. A place names a change rather than counting them: after an undo new typing cuts the old way forward off, and a count would come back to a number it had before while the document is somewhere it has never been. The document keeps the copy made at open and its typed buffer for as long as it is open, and no save moves it onto another, so the history, which points into those two and never into the file, can walk to any state the document has been in since it opened with nothing new stored, and nothing done to the file — saving it, Save as, another app writing it — can reach it. That costs the copy held until the document closes however much of it has been replaced, the typed buffer no longer let go at a save, and the pieces no longer collapsing at one.
- **The history and the pieces each have a limit of their own.** The history holds as many changes as a share of the heap can, out of reach on a phone with memory to spare and inside the heap on one without, and when it is full the oldest change falls off, which costs nothing. A change that falls off the history is still in the text, so its pieces stay, and the only way to have fewer is to copy text into one place: the cheapest spot, the smallest neighbouring pieces, and not the oldest change, which can sit between two half-gigabyte pieces. A merge is invisible to the history, which works in document offsets and in the pieces it took out, and a merge changes neither.
- **What a plain document typed moves onto disk once there is enough of it, and an encrypted one's never does.** Merging copies the file's own bytes into it, and over a long session on a large file that can be much of the file, which the heap cannot hold. It goes into app storage the way the private copy does, where nothing but the document can reach it, and until there is enough it stays in memory, so ordinary editing never touches the disk. **A disk that refuses it leaves it in memory** and the move is tried again later: a full disk costs heap and never an edit, since what was typed has nowhere else to be kept.
- **Everything under the last row is a tap target that puts the cursor at the end of the document**, which is what tapping past the end of the text means anywhere else. It belongs to the list, which is always the size of the screen, and not to blank space after the text, which a document shorter than the screen — one just opened, and every new one — would leave too short, with the one empty line at the top as the only way in.
- **The window asking for focus is addressed to one window, and it stands until that field actually holds focus.** Cutting the window leaves two rows alive for a moment and both are asking; the one about to be disposed must not take the ask with it, and neither may a matching one that is disposed or cancelled before it gets there, or the field that survives is never focused and the keyboard shuts with no way back.
- **The activity takes configuration changes itself rather than being rebuilt**, rotation and a switch into dark mode included. A rebuild drops the open document, and nothing could bring it back: the descriptor the document reads through and the pieces standing on it are not something a saved instance state can hold, and no persistable permission is held that would let the file be opened again. That holds until there is somewhere to persist to, and even then re-opening a file loses unsaved edits, so it is the wrong answer for an editor.
- **There is one open file, always, and unsaved edits are never thrown away without asking.** Whatever opens a file — New, Open, or another app handing one over — replaces the document on screen rather than adding another copy of Edit beside it, and anything that would drop unsaved edits asks first. That holds everywhere the app can see it coming. What it cannot see is out of reach: swiping Edit away from recents, or the system killing it in the background, gives the app no chance to ask.
- **While the keyboard is up the screen is the text's, and only something worth seeing mid-sentence takes a line of it back.** In landscape the keyboard leaves a few lines, and whatever stays on screen while typing comes out of them. The file row and the name bar go with the keyboard. The bar says which file is open or what just happened to it, and what it says decides whether it stays: a file just opened or just saved holds it over the keyboard briefly, and a warning — an open or a save that failed — holds it until a moment after the user next presses the screen or changes the text. Waiting for the user rather than for a clock is what stops a warning coming and going while nobody was looking, and the moment after is what stops the touch that noticed it from taking it away. Opening and saving while they run hold nothing. The bar pushes the text down rather than covering it, so the cursor can never be under it.

## Known limits of the current editor

A number belongs to a limit for good and is never given to another, so the gaps are limits that have been answered or moved elsewhere, and the numbering is not to be tidied up.

5. No persistable URI permission is taken, so a file cannot be reopened after the process dies. Harmless until there is a recent-files list to reopen from.
8. **A selection a keyboard sets itself, rather than asking for with keys, reaches only as far as the window.** A swipe from backspace or a keyboard's own select keys build each step on what the field holds, and the field holds the window and nothing past it, so the end being carried stops at the window's edge, while an end already beyond it stays where it is. The same goes for a keyboard putting the cursor down itself: one that lets go of a selection straight after copying it, as Samsung's does, puts the cursor where the field's part of the selection ends, which is the window's edge rather than the selection's end when it reaches past the window. Shift and the arrows, select all however it is asked for, and dragging a handle have no such limit. It lasts until the window can move without the keyboard noticing (see Not started).

## How the text is laid out

- **There is no buffer.** The document is a sequence of pieces over two places — ranges of the private copy of the file, and ranges of what has been typed — and an edit rewrites the sequence rather than any bytes. What is in memory measures the editing and not the file.
- **Chunks.** The document is indexed into chunks cut on line breaks, so wrapping inside a chunk is what wrapping the whole document would have produced. A line with no break in it is cut at a space, the only place a boundary is visible, and never in the middle of a character. A chunk holds about as much text whatever the file is written in. After an edit only the chunks it fell inside are indexed again, widened to whole chunks, or a boundary would land in the middle of a line.
- **Rows.** Only the chunks on screen are ever measured, a row's text is decoded when it is drawn and thrown away when it scrolls off, and which rows there are is worked out from the index rather than held as a list, which on a large document would be hundreds of thousands of objects rebuilt on every commit.
- **The window.** One slice of the document around the cursor is a real text field and takes all the keyboard's input, so the IME, its suggestions and autocorrect are the platform's and not ours. Touches are not the field's: they reach the editor first, whatever row they land on, the window's included. Every other row is read-only and turns into the window when tapped. It is consulted on every change to the field rather than on every move of the cursor, which is the only way deleting forwards or pasting could ever reach it.
- **What the window commits is the run the typing actually touched, not the whole window.** A window is a few thousand bytes of which almost none was typed, and committing all of it would fill what was typed with text nobody typed and leave the file's own bytes for that run behind, which is exactly what byte pieces exist to avoid.
- **The window's size is a dial.** It is the only text a keystroke lays out again, so a larger window costs typing latency and buys fewer cuts while typing. How far a selection reaches does not depend on it, but for one a keyboard sets itself (limit 8).

## File size

Two caps, both refused with our own message: the whole of what an `Int` can address for plain files, and a small one for encrypted ones (see the design decisions). The format is sniffed from the first bytes before the size is checked against that format's cap, so the same file can open as text and be refused as an encrypted one. The size comes from our own descriptor rather than from a provider column, so there is no second opinion to be wrong.

**Nothing in memory scales with the file.** The heap holds the chunk index, the pieces, the history, what has been typed up to the point it moves onto disk, and the one slice the window is showing. The index is the only one of those that grows with the file, at about one part in five hundred.

What is left is:

1. **`Int` addressing**, which is the cap. Every offset in the document, the index and the pieces is an `Int`, so 2 GB is the ceiling and the cap is set at it. Going past it means `Long` offsets through all four pure files, and it buys files this app almost certainly should not be opening.
2. **Patience with opening**, which is what actually bites first — two whole-file passes of about the same cost, the private copy and then the index, so a gigabyte is many seconds with nothing on screen. Incremental indexing is the answer for the index and is not written yet.
3. **App storage.** The copy a document reads costs the file's size for as long as it is open, however much of it has since been replaced, and a typed buffer that has moved onto disk costs what it holds. A save is three passes over the file: hashing it, writing the document over it and reading it back. Saving with nothing changed since the file was last in step is the hash alone.

**Nothing here depends on the heap the device hands out but the depth of the history**, which is a share of it.

## Not started

- **Undo must not depend on where the window was cut.** A cut is the editor's own choice, made in the background, and today it splits what one press of undo takes back. Nothing the user did not choose may shape what undo does.
- **A paste, a cut or a replace is an undo step of its own.** Today runs are joined by position and time alone, so a paste where the user was just typing joins that run and one press takes both back.
- **The text field is to keep no history at all.** Today it keeps one between cuts, cleared only when the window is cut, and it is out of reach only because the undo keys are taken before the field sees them.
- **The keyboard must not see the window being cut.** Where the window sits and how much it may hold are memory and display concerns, and the keyboard has to work as if neither existed. Today a cut replaces the field, so the keyboard gets a new input session: its panels close, the clipboard one included, and the word being composed is committed mid-word. The keyboard closing and opening again also resizes the list under the field, and the list scrolls to keep the field that has focus in view, which can leave the cursor off the screen until the next keystroke; typing over a selection that reaches outside the window is where that still shows. At the end of a document the size ceiling is the only thing that ever cuts, so plain writing hits this every ten thousand characters or so. It matters beyond the interruption: cuts that cost nothing could come far more often, and a smaller window is a cheaper keystroke.
- **Tapping a line after scrolling away from where you typed makes the text jump.** Type something, scroll down until the place you typed is off the top of the screen, then tap a line further down: the cursor lands on the right spot, but the tapped line jumps to about a third of the way down the screen instead of staying under the finger. The same tap without typing anything first moves nothing.
- **Incremental indexing.** The largest remaining win, and one of the two whole-file passes an open makes; the copy is the other, so on its own it halves the wait rather than ending it, and to take the rest it would have to follow the copy as it is made. Index the first stretch, show the rows there are, and go on behind the list: the row count the list insists on is a count and not the final count, and rows added at the end disturb nobody. What it has to handle is an edit landing while the tail is still being indexed, which moves every offset after it. Indexing today also reads the whole file into short-lived arrays once over, which a steady trickle would replace.
- **Nothing asks before unsaved edits are thrown away.** New and Open replace the document on the spot, and Back closes Edit, all with no warning. The question is exact rather than a guess: whether the document stands anywhere on the line of changes other than the base.
- **Opening a file from another app while Edit is already open starts a second copy of Edit instead of replacing the document.** The new file opens on top, the old one stays open underneath with its edits, and Back returns to it, so the same file can end up open twice. Asking again for the file the first copy was opened with opens nothing at all: Edit only comes to the front, showing whatever the top copy holds.
- **Save as as the way out when saving is refused.** A file the app was handed read-only fails with `could not save: <package> has no access to <uri>`, which is accurate and useless. It should offer Save as instead, which is the same branch the collision dialog already has. The same thing happens after a file is replaced under an open document, since the grant that came with the intent belonged to the file that was there.
- Editor UI: find and replace, a scrollbar or some sense of where in the file you are. Find is the next one worth doing.
- Encryption: passphrase entry, KDF, envelope format, decrypt-on-open / encrypt-on-close. The split is in place, and the magics sniffed are age's only provisionally.
- **An encrypted document's cap is checked as it opens and never again.** The whole document lives in what was typed, which holds its text and whatever the history still names, and with the history spanning saves a save no longer lets any of that go, so editing can grow it past the cap, as far as typing can. The text itself can pass the cap the same way, which grows the one field it is laid out in past the size the cap was set for, and a save would then write a file that opening refuses as too big.
- Device-to-device backup posture. Backup being off stops cloud backup on every supported version, but from Android 12 it does not stop device-to-device transfer, which needs an exclusion of its own; lint flags the same thing. The app persists nothing at all today, so there is nothing to leak; do this when it first stores something, such as recent files, SAF permission grants or settings.
- **A scroll cancelled while the editor follows the cursor ends the following for good.** The list refuses a scroll while a finger drag holds it, and the editor scrolls both to bring the cursor back on screen and, with the cursor still on screen, for the nudge that lets the window reach back over the top row. Text arriving mid-drag at either moment — a second finger, a hardware keyboard, voice typing finishing — would silently stop it: from then on keystrokes are not recorded as they are typed and the window stops following. A fling does not do it. Read off the code and not yet seen on the phone.
- **The process dying in the middle of a write leaves the file half-written.** Killed for memory once in the background, swiped away, a flat battery: writing over a file through the provider cannot be made atomic. The usual guard is a foreground service for the length of a save, which makes a kill far less likely.
- **A large paste holds the screen for as long as laying it out takes.** What is pasted goes into the window's field as one edit, and the field lays all of it out before the window is cut back to size, so the pause grows with the paste: at a megabyte it is long enough for the system to offer to close Edit. The ceiling on the window answers every keystroke after the paste, and nothing answers the paste itself.
- **A clip that is a link to a text file is read whole as it is pasted.** The system turns such a clip into text by reading everything the link points at, in one go and on the main thread, before the editor sees any of it, so a link to a large file freezes Edit or runs it out of memory. Nothing in the clipboard's own limits catches it, since the clip itself is only a link.
- **Compacting what was typed runs on the main thread and costs what it keeps.** While it is all in memory that stays small; once it is on disk and holds hundreds of MB, it is a pause of seconds.
